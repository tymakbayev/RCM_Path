## Связь с адресным движком

Модель применяет схему G + P + R к содержимому записей. В ноябре 2026 та же схема перенесена на адресный (индексный)
слой существующей СУБД ([`STAGE1.md`](../experiments/STAGE1.md) §2,
[`STAGE1_postgresql_branch.md`](../experiments/STAGE1_postgresql_branch.md)):

    h = hash64(ключ, зерно)               G: вычисляется из ключа, не хранится
    slot = P(h)                           P: каскад битовых карт (минимальная совершенная хеш-функция), ~3 бита на ключ
    (отпечаток, страница) = D[slot]       R: остаток, поле фиксированной ширины на ключ (8 + ⌈log2 страниц⌉ бит)

Отчёты STAGE1 исходят из вывода §19.2c `memory_math.md`: индекс поиска выгоднее выводить, чем хранить (хранимый индекс
по 16 байт на объект снижал коэффициент сжатия того проекта с 11,5× до 3,5×). Там же уточнён тезис «индекс = 0 байт
на диске»: для произвольного размещения, не связанного с ключом, точное отображение «ключ → позиция строки» требует
около log2(n) − 1,44 бита на запись, а «ключ → страница» при примерно равномерно заполненных страницах около
log2(число страниц) бит (`STAGE1.md` §2.1).
