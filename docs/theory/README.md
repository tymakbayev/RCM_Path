## Связь с адресным движком

Теория применяет G + P + R к содержимому. В ноябре 2026 автор перенёс тот же принцип на адресный (индексный) слой
существующей СУБД ([`STAGE1.md`](../experiments/STAGE1.md) §2, [`STAGE1_postgresql_branch.md`](../experiments/STAGE1_postgresql_branch.md)):

    h = hash64(ключ, зерно)               G: порождается из ключа, не хранится
    slot = P(h)                           P: каскад битовых карт (минимальная совершенная хеш-функция), ~3 бита на ключ
    (отпечаток, страница) = D[slot]       R: остаток, поле фиксированной ширины на ключ (8 + ⌈log2 страниц⌉ бит)

Оба отчёта STAGE1 отталкиваются от вывода §19.2c `memory_math.md`: индекс поиска лучше выводить, а не хранить
(хранимый индекс по 16 байт на объект снижал коэффициент сжатия того проекта с 11,5× до 3,5×). И уточняют тезис
«индекс = 0 байт на диске»: для произвольного размещения, не связанного с ключом, точное отображение «ключ → позиция
строки» стоит около log2(n) − 1,44 бита на запись, а «ключ → страница» при примерно равномерно заполненных страницах —
около log2(число страниц) бит (`STAGE1.md` §2.1).
