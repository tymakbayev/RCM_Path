## 1. Вопросы

- **H-A.** Sidecar А: таблица в порядке поступления, адресный файл строится из `SELECT k, ctid`, строка читается
  Tid Range Scan по одной странице с перепроверкой ключа. Адрес = совершенная хеш-функция P + отпечаток + номер
  страницы кучи. Узкая гипотеза о байтах, обращениях к буферам и правильности:
  - 100% правильных ответов;
  - адрес ≤ 8 байт на запись и ≤ 0,25 размера B-tree и хеш-индекса PostgreSQL на тех же данных;
  - одно обращение к основной куче на запрос;
  - открытие без операций, зависящих от N;
  - в динамике — ограниченная дельта, периодическая полная пересборка адреса и обращений не больше, чем у B-tree на
    том же потоке операций.
  - «ПРОХОДИТ» не означает эксплуатационной выгоды: задержки и стоимость пересборок здесь описательные.
- **H-Б.** Sidecar Б: таблица загружена по корзинам хеша ключа, страница вычисляется из ключа по таблице начал
  корзин, доли байта на запись. Сколько это стоит в обращениях к куче и в перезаписи таблицы при обслуживании?
  Как это соотносится с готовым приёмом PostgreSQL — таблицей, упорядоченной по ключу, плюс BRIN?

## 2. Данные

- Поток записей — копии корпуса E19/E20 (тот же генератор, что в E21). Копия k = 0, 1, …:
  - строится `e19.build_corpus(2026 + k, 0.0)` при `e19.TIME_UNIT_MS = 1`, затем `e20.to_observations`;
  - эпоха `e{k+1}`, `event_uuid = derived_event_uuid(device_id, эпоха, device_seq)`;
  - время сдвинуто на k · span, где span — длительность копии 0 плюс 1 сутки.
- ЗАМЕР: у копий 2026 и 2027 общих субъектов 42 из ~2100. С общей эпохой совпали бы 45 126 событий, поэтому эпоха
  своя.
- Строка — одно утверждение (claim):
  - `seq bigint` — номер поступления;
  - `k uuid = memory_id(event_uuid, claim_index)`;
  - `v integer` — версия, начиная с 1;
  - `payload text` — канонический JSON полей наблюдения, источника и утверждения (sort_keys, без пробелов,
    ensure_ascii=False).
- Наборы:
  - N1 = 1 000 000 и N10 = 10 000 000 первых записей потока, в отдельных таблицах;
  - записи для динамики берутся сразу после N10;
  - пилот P0 — первые 100 000 записей.
- Генератор пишет поток прямо в `psql … -c "COPY … FROM STDIN"`, без промежуточного файла.
- Дубликат ключа — ошибка генерации.
- Сообщаются: распределение длины payload (минимум, p50, p99, максимум), размер TOAST-отношения и число
  TOAST-значений (R5).
- Ограничение: разные зёрна E19 дают разные имена, но общие шаблоны — одно семейство синтетических данных.

## 3. Таблицы и опорные индексы

- Таблица:
  - `CREATE TABLE … (seq bigint NOT NULL, k uuid NOT NULL, v integer NOT NULL, payload text NOT NULL)
    WITH (autovacuum_enabled = false)`;
  - загрузка — COPY в новую пустую таблицу, затем `VACUUM (ANALYZE)`;
  - `VACUUM FULL`, `CLUSTER` и сторонние DDL запрещены;
  - первичного ключа нет.
- Опорные индексы. Каждый строится, измеряется и удаляется по очереди на той же таблице (те же ctid); fillfactor
  записывается фактический:
  - B-tree: `CREATE UNIQUE INDEX … USING btree (k)`, штатный fillfactor 90;
  - хеш-индекс: `CREATE INDEX … USING hash (k)`, штатный 75.
  - Запрос — `SELECT v, seq, payload FROM t WHERE k = $1`; план проверяется: Index Scan по нужному индексу.
- BRIN-контроль для Б (R10), только N1, описательно:
  - копия таблицы N1, загруженная в порядке k (`INSERT … SELECT … ORDER BY k` в новую таблицу);
  - `CREATE INDEX … USING brin (k) WITH (pages_per_range = 1)` и `= 4`;
  - измеряются размер, план, обращения к куче и перепроверки ключа;
  - это другое размещение, и его цена называется прямо.

## 4. Sidecar

### 4.1. Общее

- Хеш ключа:
  - `lo`, `hi` — 16 байт uuid как два u64 little-endian;
  - `h = splitmix64(lo ^ splitmix64(hi ^ seed))`, арифметика по модулю 2^64;
  - зерно — в заголовке.
- Заголовок адресного файла:
  - магия, версия, OID таблицы, relfilenode, номер поколения, число строк, число страниц, водораздел W, зерно,
    параметры;
  - CRC32 заголовка;
  - BLAKE2b-256 всего файла в концовке. Пишется при сборке, проверяется командой `verify`; при открытии не
    проверяется, иначе открытие стало бы O(N).
- Манифест — JSON:
  - поколение, имя файла, его sha256, OID, relfilenode, W, имя дельта-индекса, имя таблицы (Б);
  - публикуется через `os.replace`.
- Открытие:
  - чтение манифеста, CreateFile + mmap, разбор заголовка, представления numpy поверх mmap;
  - один запрос к `pg_class` сверяет OID и relfilenode; несовпадение — отказ открытия, а не неверный ответ.
- Операций, зависящих от N, при открытии нет — это проверяется разбором кода в отчёте.
- Поколения (R6). Пересборка идёт при остановленных писателе и читателях:
  1. дождаться завершения активных транзакций (`pg_stat_activity`);
  2. пересобрать;
  3. опубликовать манифест;
  4. все клиенты заново открывают sidecar и заново готовят выражения.
  - Старый дельта-индекс (А) или старая таблица (Б) удаляется только после переоткрытия всех клиентов.
- Единственный писатель (R1). Ключ уникален среди видимых строк. Это гарантирует писатель: INSERT выполняется
  только после поиска, ответившего «нет», а уникального индекса нет.

### 4.2. Вариант А (JLMADR01)

- Каскад битовых карт, γ = 2.0:
  - на уровне l ключ попадает в ячейку `((splitmix64(h + (l+1)·0x9E3779B97F4A7C15) >> 32) · m_l) >> 32`, где
    `m_l = max(64, ⌈γ·n_l⌉)`;
  - ключ, оставшийся один в ячейке, получает бит 1, остальные идут дальше;
  - уровней не больше 64.
- Ключи, не размещённые после 64 уровней (включая пары с одинаковым полным h), идут в список исключений: 16 байт
  ключа и u32 страницы, по возрастанию ключа. Список входит в M1.
- Ранг. Блок 64 байта: u32 ранга и 480 бит карты, так что проба уровня касается одной строки кэша. Номер слота — ранг
  бита.
- D[slot] = отпечаток f = 8 бит (младшие биты h) | номер страницы r = ⌈log2(число страниц)⌉ бит, упакованы подряд.
- Поиск страницы:
  1. исключения (двоичный поиск);
  2. P → D;
  3. совпал отпечаток → страница r;
  4. не совпал → строки нет в адресе.

### 4.3. Вариант Б (JLMHPL01)

- Корзина ключа — `h >> (64 − b)`, где 2^b — ближайшая степень двойки к (число строк / среднее число строк на
  страницу таблицы А). Ограничение 1 ≤ b ≤ 32.
- Таблица Б — всегда новая и пустая. В неё загружаются строки в порядке (корзина, seq):
  - клиент читает `(seq, k)`, считает корзины и пишет через COPY временную таблицу `(seq, pos)`;
  - затем `INSERT INTO t_b SELECT t.* FROM t JOIN ord USING (seq) ORDER BY ord.pos`;
  - затем `VACUUM (ANALYZE)` и чтение `SELECT k, ctid`.
- Метаданные — массив u32 длиной 2^b + 1:
  - start_j = страница первой строки корзины j;
  - пустая корзина получает start следующей непустой;
  - последний элемент — последняя страница таблицы.
- Инвариант (R8): для каждой строки start_j ≤ страница ≤ start_{j+1}; проверяется исчерпывающе после каждой сборки.
  Нарушение — результат «схема границ непригодна на этом размещении». Диапазоны молча не расширяются.
- Поиск: страницы [start_j, start_{j+1}] одним Tid Range Scan `ctid >= (start_j,0) AND ctid < (start_{j+1}+1,0)`.
  Сообщается распределение длин корзин в страницах.

### 4.4. Простые опорные sidecar (описательно)

- **SORT:** отсортированный по `h >> 32` массив u32 плюс u32 страниц, 8 байт на запись. Только байты и C1 (R11).
- **EF (расчёт):** точный размер кода Элиаса–Фано для отсортированных 32-битных префиксов плюс r бит страницы, по
  фактическим данным (R12 из 227).
- Вариант А-G8 из редакции 1 исключён до прогона (R11: урезается первым).

### 4.5. Запросы

- Статическое чтение (нет дельты), А и Б: `SELECT ctid, v, seq, payload FROM t WHERE ctid >= $2 AND ctid < $3
  AND k = $1`.
- Чтение с дельтой (R7):
  `(SELECT ctid, v, seq, payload FROM t WHERE k = $1 AND seq > W) UNION ALL
   (SELECT ctid, v, seq, payload FROM t WHERE ctid >= $2 AND ctid < $3 AND k = $1) LIMIT 1`.
  - Без ORDER BY: Append выполняет ветви по порядку и останавливается на первой строке. Это верно, потому что видимая
    версия ключа одна — любая найденная строка и есть ответ.
  - План Limit → Append без Sort, а также пропуск второй ветви при попадании в дельту, проверяются в пилоте P0.
  - Если отпечаток не совпал, выполняется только первая ветвь.
- UPDATE и DELETE по ключу (R1) — в одной транзакции писателя:
  1. поиск, возвращающий ctid;
  2. `UPDATE t SET payload = $3, v = v + 1, seq = nextval('…') WHERE ctid = $2 AND k = $1` или
     `DELETE FROM t WHERE ctid = $2 AND k = $1`;
  3. 0 изменённых строк при найденном ctid — ошибка проверки.
  - Ключ не найден → UPDATE и DELETE не выполняются, ответ «нет строки».
  - Планы (Tid Scan) проверяются в P0 для ключа из адреса, из дельты и отсутствующего.
- У B-tree-контроля те же команды выполняются с `WHERE k = $1` через его индекс.

## 5. Динамика (база N1; А, Б и B-tree-контроль)

- Дельта (А и Б) — частичный B-tree `CREATE INDEX … (k) WHERE seq > W` с литералом W в определении и в тексте
  запросов.
- Операции. Каждая получает следующий `seq`:
  - INSERT = поиск («нет») + вставка, v = 1;
  - UPDATE = поиск + изменение по ctid (§4.5), строка уходит в дельту;
  - DELETE = поиск + удаление по ctid. Мёртвую версию отсекает MVCC.
- Нагрузка — 500 000 операций в случайном порядке (seed 13):
  - 250 000 INSERT новых ключей потока;
  - 150 000 UPDATE ключа, равномерно выбранного из живых на этот момент;
  - 100 000 DELETE ключа, равномерно выбранного из живых;
  - транзакции по 1 000 операций.
  - Один и тот же поток операций применяется к трём копиям N1: А, Б и B-tree-контроль (таблица с полным
    уникальным B-tree, без sidecar).
- Политика VACUUM одинакова у всех трёх (R3): autovacuum выключен; обычный `VACUUM` выполняется у каждой копии сразу
  после операций 240 000 и 480 000.
- Пересборки (А и Б) — после операций 120 000, 240 000, 360 000 и 480 000, плюс финальная после 500 000. Всего пять;
  при каждой остановлены писатель и читатели (§4.1).
  - А: в REPEATABLE READ берутся W' = max(seq) и `COPY (SELECT k, ctid FROM t) TO STDOUT`; затем сборка файла,
    fsync, `CREATE INDEX` дельты с W', манифест, переоткрытие клиентов, `DROP INDEX` старой дельты.
  - Б: живые строки переписываются в новую таблицу в порядке корзин (§4.3), затем новая таблица корзин, новая дельта,
    манифест, переоткрытие клиентов, `DROP TABLE` старой.
- Контрольные точки — одинаковые для трёх копий, с C4 и замерами M6 (R2):
  1. база;
  2. непосредственно ПЕРЕД каждой пересборкой (120 000, 240 000, 360 000, 480 000 и 500 000 операций): максимум
     дельты;
  3. сразу ПОСЛЕ каждой пересборки;
  4. рестарт PostgreSQL (`pg_ctl restart -m fast`) после финальной пересборки и повторное открытие клиентов.
- Размер дельта-индекса (`pg_relation_size`) и число живых строк дельты пишутся на границе каждого пакета из 1 000
  операций.
- Аварийное завершение во время публикации — вне контракта A2.
- Сценарии на таблице 10 000 строк с ожидаемыми ответами. Каждый — до и после пересборки:
  - UPDATE ключа, уже лежащего в дельте → новая версия;
  - три UPDATE подряд → v = 4;
  - UPDATE → DELETE → «нет»;
  - DELETE → INSERT того же ключа → новая строка, v = 1;
  - повторный DELETE → «нет строки», 0 изменений;
  - UPDATE отсутствующего ключа → «нет строки», 0 изменений;
  - DELETE и UPDATE → обычный VACUUM → INSERT и UPDATE с проверкой фактических ctid (повторное использование места)
    → поиск всех затронутых и соседних ключей (R8).

## 6. Проверки правильности

Без нуля ошибок вердикта нет (§8). Провал — исправить, повторить, раскрыть в отчёте.

- **C1, исчерпывающая.** Для каждой строки из `SELECT k, ctid`:
  - А и SORT указывают её страницу;
  - для Б выполняется инвариант §4.3.
- **C2, сквозная.** 100 000 присутствующих ключей (seed 11):
  - `(v, payload)` побайтно равны эталону — сгенерированным данным, а в динамике словарю ключ → (v, sha256 payload);
  - на статическом N1 перекрёстно равны ответу через B-tree.
- **C3, отсутствующие.** 100 000 случайных uuid (seed 12), которых нет по эталону: ответ «нет».
- **C4, динамика.** В каждой контрольной точке §5 — фиксированные выборки:
  - 20 000 живых ключей (seed 21 + номер точки), с разбивкой: неизменённые из адреса, обновлённые, вставленные;
  - 20 000 удалённых (seed 41 + номер точки; все, если их меньше);
  - 20 000 отсутствующих (seed 61 + номер точки);
  - все сценарии §5.
- **C5, мутанты и краевые случаи** (таблица 100 000 строк). Мутанты со свидетелем; каждый должен быть пойман C1–C3
  на пути поиска свидетеля:
  - (а) D свидетеля указывает на страницу без него;
  - (б) ранг блока свидетеля на 1 меньше;
  - (в) отпечаток не сравнивается, а `k = $1` убран из запроса;
  - (г) start корзины свидетеля в Б сдвинут на 1 страницу вперёд;
  - (д) исключения не просматриваются, при одной искусственной коллизии полного h.
- Краевые случаи C5:
  - границы 480-битных блоков и слов u64;
  - D, пересекающий границу слова;
  - первый и последний слот;
  - ключи SORT с одинаковым 32-битным префиксом на разных страницах;
  - пустая корзина Б;
  - отсутствующий ключ, не встретивший единичного бита ни на одном уровне.
- splitmix64: numpy против скалярного Python с маской 2^64 − 1 на 0, 1, 2^63, 2^64 − 1 и 10 000 случайных значений.

## 7. Замеры

### M1, байты (R4, R9)

- «Основная структура», байт на запись:
  - sidecar — весь файл с исключениями, плюс манифест и дельта-индекс (main fork);
  - PostgreSQL — `pg_relation_size(индекс)`, main fork.
- «Полный дисковый бюджет»: все forks индексов (`pg_total_relation_size`), сосуществование поколений при
  пересборке, старая таблица Б до удаления, временные таблицы и сортировка.
- Таблица (`pg_table_size`, включая TOAST) — отдельно, один раз в каждом варианте.
- В динамике — на живой ключ, плюс число живых и мёртвых кортежей (`pg_stat_user_tables`) и живых строк дельты.
- Пиковые RSS клиента и временный диск при сборке.
- EF — расчётная строка. Фактический fillfactor каждого метода.

### M2, открытие (R6)

- (а) Новый процесс при тёплом кэше ОС: время от открытия манифеста до готовности sidecar, затем до ответа на первый
  запрос. Подключение к PostgreSQL — отдельно. 21 запуск, медиана и максимум.
- (б) После `pg_ctl restart` (shared_buffers пусты, кэш ОС тёплый): обращения к буферам (read и hit по верхнему
  узлу) и время исполнения первого запроса, среднее по следующим 200. По 3 рестарта на метод (А, Б, B-tree, хеш) и
  размер.
- (в) Число 4-КиБ страниц sidecar, которых коснулся первый запрос (счётчик в обёртке доступа).
- Независимость от N утверждается только для двух измеренных размеров плюс разбор операций открытия.

### M3, запрос (R4, R5)

- На каждый метод и размер — 100 000 запросов C2 в один поток, подготовленные выражения, два прохода, учитывается
  второй:
  - время клиента p50 / p95 / p99 с полным получением результата;
  - для sidecar отдельно — время вычисления адреса в клиенте (Python) и пакетная скорость numpy.
- 2 000 из них — с `EXPLAIN (ANALYZE, BUFFERS, SERIALIZE TEXT, FORMAT JSON)`:
  - время исполнения на сервере;
  - обращения к буферам по ВЕРХНЕМУ узлу плана, без суммирования дерева;
  - буферы планирования — отдельно.
- Разделение по отношениям — отдельный изолированный пакет из 2 000 запросов в своём соединении:
  - разность `pg_statio_user_tables` (heap, toast) и `pg_statio_user_indexes` до и после;
  - сброс статистики через `pg_stat_force_next_flush()`, чтение из нового снимка; методика проверяется в P0.
- Определения:
  - обращение к буферу = hit + read, а не число различных страниц и не физический ввод-вывод;
  - обращения к метастранице хеш-индекса и к карте видимости учитываются только фактические;
  - прикладного кэша нет.

### M4, сборка

- Время CREATE INDEX (B-tree, хеш, BRIN).
- Sidecar — отдельно чтение `SELECT k, ctid` и построение.
- Б — загрузка в порядке корзин.

### M6, динамика

В каждой контрольной точке §5:
- M1 на живой ключ (основная структура и полный бюджет);
- обращения к буферам на запрос по категориям ключа (неизменённый, обновлённый, вставленный, удалённый,
  отсутствующий), с разделением дельта, адрес и куча по методике M3;
- время клиента p50 / p95 / p99;
- время каждой пересборки, прочитанные и записанные байты (разность `pg_stat_io` или размеров отношений);
- средняя стоимость обслуживания на операцию с учётом пересборок;
- время рестарта до первого ответа.

### Пилот P0 (100 000 строк, до основного прогона, не вердикт)

- Проверяет:
  - планы §4.5 (Limit → Append без Sort, пропуск второй ветви; Tid Scan в UPDATE и DELETE);
  - методику `pg_statio`;
  - инвариант Б на реальном распределении длины payload;
  - время каждого шага и пиковый диск.
- Если план или методика расходятся с протоколом, исправляется реализация в рамках протокола. Если нужно изменить
  метод — датированное приложение ДО основного прогона.
- По P0 выносится решение о бюджете: если расчётное время N10 больше 6 часов, урезаются число рестартов (3 → 1) и
  выборки M3 (100 000 → 20 000); это фиксируется в приложении до прогона. N10, C1, точки перед пересборкой, сценарии
  VACUUM и B-tree-контроль не урезаются.
- Пиковый диск (ВЫВОД, уточняется в P0): таблицы N10 А и Б ≈ 4 + 4 ГБ, сортировка при загрузке Б ≈ 4 ГБ, индексы
  ≈ 0,4 ГБ, WAL ≤ 1 ГБ, таблицы N1 (три копии и BRIN-копия) ≈ 1,6 ГБ. Итого около 15 ГБ при 35 ГБ свободных на C:.

## 8. Правило решения

Три исхода: **ПРОХОДИТ**, **НЕ ПРОХОДИТ** (с названием критерия), **НЕ УСТАНОВЛЕНО**. Последний — если
обязательные проверки не завершены или ошибка реализации не устранена; одинаково для А и Б. Если N10 не завершён,
выводы только по N1, итог гипотезы — НЕ УСТАНОВЛЕНО.

- **H-A ПРОХОДИТ**, если выполнены все условия:
  - **A1.** C1–C4 без ошибок по матрице (N1 и N10 статически; все контрольные точки и сценарии на N1), C5: все
    мутанты пойманы и краевые случаи верны.
  - **A2.** Основная структура А ≤ 8,0 байта на запись и ≤ 0,25 · min(B-tree, хеш) на N1 и на N10.
  - **A3.** На запрос присутствующего ключа обращений к буферам основной кучи ≤ 1,02 по разделению M3 (TOAST
    сообщается отдельно), отсутствующего — ≤ 0,01 на N1 и N10. Медиана M2(а) на N10 ≤ 50 мс и
    ≤ max(2 · медиана N1, медиана N1 + 5 мс); в разборе открытия нет операций, зависящих от N.
  - **A4a.** В КАЖДОЙ контрольной точке основная структура (адрес + дельта) на живой ключ ≤ 8,0 байта.
  - **A4b.** В КАЖДОЙ контрольной точке среднее число обращений к буферам на запрос живого ключа (по верхнему узлу,
    равная смесь категорий из выборки C4) ≤ того же у B-tree-контроля в той же точке.
  - Не выполнено A2, A3, A4a или A4b → НЕ ПРОХОДИТ с названием критерия.
- **H-Б ПРОХОДИТ**, если:
  - C1–C5 для Б без ошибок;
  - инвариант §4.3 выполняется на всех размещениях;
  - метаданные Б ≤ 1,0 байта на запись на N1 и N10;
  - обращений к основной куче на запрос присутствующего ключа ≤ 2,5 на N1 и N10;
  - в каждой контрольной точке выполняются A4a и A4b для Б.
  - Иначе — НЕ ПРОХОДИТ с названием критерия.
- Описательно, без влияния на вердикт:
  - задержки M3;
  - SORT и EF против А;
  - BRIN-контроль против Б;
  - хеш-индекс в динамике (не измеряется: его рост называется ограничением);
  - время и байты пересборок А (адрес) и Б (перезапись таблицы);
  - сравнение открытия с нынешним стартом движка (ВЫВОД из E21: около 42 тыс. записей/с).
- Выводы ограничены парой «глобальный адрес А против корзин Б» на одной таблице и формулой «меньше измеренных
  B-tree и хеш-индекса в N раз», а не «лучший компактный адресный слой PostgreSQL» (R10).

## 9. Прогноз (до кода)

- Строк на страницу — 19–23; страниц ≈ 45–53 тыс. (N1) и 450–530 тыс. (N10); r = 16 и 19 бит. TOAST — 0 значений
  (payload около 300 байт, меньше порога 2 КБ).
- Байт на запись (основная структура):

  | Структура | N1 | N10 |
  |---|---|---|
  | А | 3,3–3,6 (точка 3,44) | 3,7–4,0 (точка 3,82) |
  | EF (расчёт) | ≈ 3,76 | ≈ 3,72 |
  | B-tree | 30–36 | 30–36 |
  | Хеш-индекс | 22–30 | 22–30 |
  | Б | 0,13–0,27 | 0,13–0,27 |
  | BRIN-контроль (N1, ppr 1) | 0,8–1,5 | — |

  - А против EF — в пределах ±10%: сама совершенная хеш-функция почти ничего не даёт против отсортированного
    массива хешей.
  - А / min(индексов) ≈ 0,12–0,16.
- Обращения к буферам на статический запрос:
  - B-tree — 4 (N1), 4–5 (N10);
  - хеш — 3;
  - А — 1,00 (куча);
  - Б — 1,5–2,2;
  - BRIN — несколько страниц индекса плюс 1–2 страницы кучи с перепроверками.
- Время исполнения на сервере: B-tree 10–30 мкс, А 5–20 мкс. Время клиента определяется круговой поездкой
  (50–150 мкс) и почти одинаково у всех методов.
- Динамика:
  - запрос неизменённого ключа ≈ 3 обращения (дельта 2 + куча 1), вставленного ≈ 3, обновлённого ≈ 3 (дельта
    отвечает, вторая ветвь пропускается), удалённого ≈ 3 (дельта 2 + старая страница 1);
  - B-tree-контроль — ≈ 4 во всех точках;
  - пик основной структуры перед пересборкой ≈ 6,5–7,5 байта на живой ключ (адрес 3,4 + дельта на 120 тыс. строк
    + раздувание дельта-индекса от UPDATE и DELETE);
  - пересборка А на 1,15 млн ключей: чтение 2–4 с плюс построение меньше 1 с;
  - пересборка Б (перезапись таблицы): 10–20 с.
- Вероятности:
  - P(H-A ПРОХОДИТ) ≈ 60%; главный риск — A4a перед пересборкой (дельта-индекс);
  - P(H-Б ПРОХОДИТ) ≈ 60%; главные риски — A4a и инвариант размещения.

## 10. Границы формулировок

- Выигрыш sidecar — в размере адресной структуры и числе обращений к буферам, а не в «отсутствии индекса». Адресный
  файл — статическая функция «ключ → страница», его байты учтены. Дельта — обычный B-tree, ограниченный T строками.
- Sidecar не встроен в планировщик: запросы переписывает клиент. Метод доступа на C (`CREATE ACCESS METHOD`) — только
  после вердикта и решения владельца.
- Задержки клиента измерены на Python + psycopg. От языка клиента не зависят счётчики обращений и время исполнения на
  сервере, но не миллисекунды открытия.
- Кэш ОС тёплый; «холодный» здесь — только пустые shared_buffers после рестарта. Холодный диск не измерялся.
- Контракт: единственный писатель, пересборка при остановленных писателе и читателях, без сторонних DDL. Конкурентная
  запись и авария при публикации — вне A2.
- Корпус синтетический (одно семейство E19). Настройки PostgreSQL по умолчанию. Одна машина (Ryzen 3600X, 32 ГБ,
  SSD C:).
- Граница из STAGE1 §2.1 уточнена (R13 из 227). log2(n!/∏c_j!) бит — объём описания произвольного назначения ключей
  страницам, если адрес не может читать данные. Последовательный просмотр обходится без описания ценой чтения всей
  таблицы. Б и BRIN-контроль не нарушают границу, а меняют размещение.
