**Поправка к формулировке варианта 1 в отчёте A4.** Там сказано «большое слияние по одной секции, читая только её
страницы». Это неверно. PostgreSQL кладёт строку на любую страницу со свободным местом, поэтому ключи одной хеш-секции
разбросаны по всей куче. Ниже разделены две оси:
- проход по таблице режется по **диапазонам страниц**;
- адрес режется по **хеш-секциям ключа**.

Перегруппировка «срезы страниц → секции ключей» требует рабочего файла на время раунда. Это цена конструкции. Она
измеряется (§5) и выносится владельцу (§8); считать её автоматически совместимой с ограничением «без скрытого
индекса» нельзя (R9).

## 1. Вопрос

Исследовательская гипотеза RCM Path (отчёт начинается с неё, отдельно от критериев): можно ли держать изменяющиеся
данные под компактной вычисляемой адресацией так, чтобы на проверенных размерах с N не росли ни стоимость
обслуживания адреса на операцию, ни **самая длинная пауза обслуживания адреса**? При этом поиск должен оставаться
«адрес → одна страница кучи», а адресные данные — компактными.

H-A5 — измеримая форма (§6) на 1 и 10 млн строк. Асимптотика и гарантированный предел задержки не проверяются: это
один прогон на размер (R6).

### 2.1. Секционированный адрес

- Хеш ключа h = `key_hash(k, SEED_SECT)` (64 бита). Секция = старшие `log2 S` бит h. Функция секций одна во всех
  поколениях и файлах.
- **Адресный файл** (база или прогон) = S независимых JLMADR01, по одному на секцию. Поиск ключа вычисляет секцию и
  пробует **один** JLMADR01 этого файла. Число пробников на уровень то же, что в A4.
- **Целевой размер секции** σ = 2¹⁷ ключей (R1). Это цель для среднего, а не предел: заполнение хеш-секции
  случайно, и работа шага включает чтение входов, удаление дублей и построение. Максимумы измеряются (§5).
  - База: S_base = 2^ceil(log2(N₀ / σ)), не меньше 1, фиксируется на весь прогон данного N. N1 → 8 (в среднем
    125 000 ключей), N10 → 128 (около 78 000).
  - Прогон из n ключей: S_run = 2^ceil(log2(n / σ)), не меньше 1. Запечатанный прогон из 30 000 ключей → 1;
    ярус 2 (около 480 000) → 4.
- Журнал прогона: ключ 16 + страница 4 = 20 байт, сортировка **по (h, k)** (R4). Секция образует непрерывный отрезок
  журнала, смещения секций записаны в манифесте. Дубли определяются по полному ключу, h вычисляется из ключа.

### 2.2. Порядок версий и слияние ярусов шагами (R2)

- **Приоритет прогона.** У каждого прогона есть приоритет — целое число, определяющее «новее». Запечатанный прогон
  получает следующий номер монотонного счётчика. Выход слияния получает **максимальный приоритет своих входов**, а не
  момент завершения. Прогоны, запечатанные после начала слияния, поэтому остаются новее его выхода.
- **Инвариант хронологии:** прогоны одного яруса образуют непрерывный по приоритетам отрезок, и любой прогон яруса t
  старше любого прогона яруса t − 1. Сливаются 4 самых старых прогона яруса t, то есть хронологически
  последовательная группа, и выход заменяет их отрезок. Поэтому одного приоритета достаточно для всего выхода.
- **Шаги.** Слияние выполняется по секциям выхода. Шаг j:
  - берёт из каждого входного журнала отрезок (h, k) в диапазоне секции j;
  - сливает: для каждого полного ключа берётся запись входа с наибольшим приоритетом;
  - дописывает отрезок в журнал выхода и строит JLMADR01 секции j.
- **Закрепление.** Одновременно идёт не больше одного слияния. Его входы закреплены: они не участвуют в другом
  слиянии и не удаляются до последнего шага. Частичный выход не становится входом другого слияния. Новое слияние
  начинается только после завершения активного.
- **Поиск во время слияния:** для ключа из уже построенной секции выхода кандидатом служит выход, для остальных —
  входы. Секции выхода публикуются по мере готовности. Входы остаются опубликованными до конца слияния и учитываются
  в S3 вместе с готовыми секциями выхода (R9).
- Не больше одного шага слияния на границу пакета.

### 2.3. Раунд большого слияния шагами (R3, R5)

- **Запуск.** Как в A4, когда монотонный счётчик зафиксированных операций с начала предыдущего раунда достигает
  f · N₀ (f = 0,1). На N10 — принудительно (§3).
- **Начало раунда** — на первой границе пакета, где нет активного слияния ярусов (ожидание входит в окно раунда):
  - принудительное запечатывание хвоста;
  - W = номер последней зафиксированной операции;
  - P₀ = число страниц кучи;
  - все существующие прогоны получают класс «до W».
  - Прогоны «до W» больше не сливаются ни между собой, ни с прогонами «после W». Слияния ярусов среди прогонов
    «после W» идут как обычно.
- **Шаги прохода** j = 0 … S_base − 1, по одному на границу пакета:
  - границы срезов b_j = floor(j · P₀ / S_base), b_{S_base} = P₀;
  - запрос `SELECT k, (ctid::text::point)[0]::int4 FROM t WHERE ctid >= '(b_j,0)' AND ctid < '(b_{j+1},0)'` в своей
    транзакции (Tid Range Scan покрывает блоки [b_j, b_{j+1}) целиком, без пропусков на границах);
  - записи (ключ 16 + страница 4) дописываются в рабочий файл своей секции.
- **Шаги построения** s = 0 … S_base − 1, по одному на границу пакета:
  - рабочий файл секции s читается. Ключ, встреченный дважды (переехал во время раунда), сохраняет любую из записей.
    Хронология сканирования для правильности не нужна, потому что переехавший после W ключ покрыт уровнями «после W»
    (§2.4);
  - строится JLMADR01 секции s нового поколения;
  - манифест публикует новую секцию s, клиенты переключают только эту секцию (R7), старая секция и рабочий файл
    удаляются.
- **Конец раунда:** после последней секции прогоны «до W» удаляются (на той же границе, в паузе), счётчик раунда
  отсчитывается от W, N₀ пересчитывается.
- **Рестарт.**
  - Посреди раунда раунд отбрасывается. Опубликованные секции остаются, прогоны «до W» сохраняются, рабочие файлы
    удаляются, счётчик раунда отсчитывается от прежнего W.
  - Посреди слияния ярусов частичный выход отбрасывается, а входы остаются: они не удалялись.
  - Аварийное завершение внутри публикации — вне контракта A4.

### 2.4. Почему раунд правильный

Инвариант A4: для каждого живого ключа хотя бы один опубликованный уровень указывает на страницу его видимой версии.

- **Ключ менялся после W.** Его самая новая запись «после W» лежит в хвосте или в прогоне «после W». Раунд эти уровни
  не удаляет, а слияния ярусов «после W» сохраняют самую новую запись по приоритету (§2.2).
- **Ключ не менялся после W.** Его страница p постоянна весь раунд, обычный `VACUUM` её не меняет (предпосылка §2).
  p < P₀, срез с p читался после W, и ключ там был. Поэтому рабочий файл секции содержит (k, p), и новая секция базы
  указывает на p.
- **Удалённый ключ** отсекается проверкой `k = $1` и MVCC.
- **До публикации новой секции** верна старая секция вместе с прогонами «до W»: это состояние A4.
- **После публикации** новая секция и уровни «после W» покрывают оба случая. Прогоны «до W» общие для всех секций,
  поэтому удаляются только после последней.
- **Страницы ≥ P₀** (куча выросла) содержат только версии, записанные после W. Они покрыты уровнями «после W».

## 4. Правильность

- **C4, применение операций, свидетели** — как в A4: 0 ошибок.
- **Сценарии** (таблица 10 000 строк, T_run = 50, σ = 256, S_base = 8). Сценарии A4 плюс:
  - ключ, обновлённый до W и после W, с переездом на страницу уже прочитанного среза;
  - ключ, переехавший во время раунда из непрочитанного среза в прочитанный (встречен 0 раз) и обратно (встречен
    2 раза);
  - INSERT во время раунда на страницу ≥ P₀;
  - DELETE во время раунда ключа, уже записанного в рабочий файл;
  - `VACUUM` с повторным использованием места посреди раунда;
  - ключи на граничных страницах срезов;
  - **R2:** начать слияние ярусов → обновить свидетель с переносом страницы → запечатать новый прогон → закончить
    старое слияние → выполнить следующее слияние → поиск;
  - поиск посреди слияния ярусов (готовые и неготовые секции);
  - **R4:** искусственная коллизия h. Тестовая функция секций с усечённым хешем даёт двум разным ключам одинаковый h,
    ключи стоят в разных входах в разном порядке;
  - **R3:** рестарт посреди раунда (часть секций базы опубликована) одновременно с активным слиянием ярусов.
- **Мутанты** (должны быть пойманы):
  - (а)–(г) из A4;
  - (д) прогоны «до W» удаляются при публикации первой секции, а не последней;
  - (е) последний срез страниц не читается;
  - (ж) прогон «до W» сливается с прогоном «после W», и результат удаляется в конце раунда;
  - (з) во время слияния ярусов поиск для неготовой секции берёт выход;
  - (и) W берётся без принудительного запечатывания, а хвост «до W» отбрасывается в конце раунда;
  - (к) выход слияния получает приоритет «момент завершения» вместо максимального приоритета входов (сценарий R2);
  - (л) слияние сравнивает только h вместо полного ключа (сценарий R4).
- Самопроверка ядра (`a2_selftest_core.py`) — повторно.

## 5. Замеры

Всё из A4 §5: обращения по категориям, `pg_statio`, кандидаты, байты, обслуживание фактическое и установившееся,
общая эффективность, открытие 21 раз, контроль R9. Дополнительно:

- **Пауза границы пакета (R7)** — всё обслуживание адреса на одной границе: подготовка, чтение входов, сортировка,
  удаление дублей, построение, сброс и fsync файлов, публикация манифеста, закрытие и открытие mmap, удаление файлов.
  - Каждый шаг измеряется по видам: запечатывание, шаг слияния, шаг прохода, шаг построения, конец раунда.
  - Сообщаются максимум, p99 и распределение, а также время пакета вместе с обслуживанием (p50, p95, p99, max).
  - **Общая максимальная остановка клиентов** — отдельно: VACUUM и рестарт показываются рядом и в S4 не входят.
- **Работа шагов (R1):** максимум и распределение числа записей входа и выхода, страниц среза, ключей секции, объёма
  сортировки и времени построения.
- **Раунд (R8).** Для каждого раунда:
  - число шагов, сумма времени, окно в операциях;
  - P₀, живые строки, размер дельты, положение относительно VACUUM;
  - прочитанный main fork по срезам, записанное и прочитанное в рабочих файлах.
- **Пик файлов адресного слоя (R9)** — отдельно от S3, и всё одновременно: опубликованная структура, рабочие файлы
  раунда, частичные выходы, закреплённые входы, сосуществование поколений. Плюс доля времени, когда рабочие файлы
  существуют. Пиковый RSS клиента — исправленным способом (`GetProcessMemoryInfo` через ctypes с правильной
  структурой). Если замер снова не работает, это раскрывается.
- **Установившееся обслуживание на операцию (R8):** `(запечатывания + шаги слияния + остаток работ раунда без
  прохода) / M + B / K`. Каждый компонент учитывается ровно один раз.
  - Первое слагаемое — из воспроизведения полного естественного цикла A5 без SQL (ниже), включая принудительное
    запечатывание на W.
  - B — измеренная сумма шагов прохода и построения в PostgreSQL на этом N: среднее по рабочим раундам и разброс,
    финальный раунд отдельной строкой.
  - K = f · N₀.
  - На N10 B взят из принудительных раундов. Поэтому B/K — амортизированная оценка при измеренном состоянии таблицы,
    а не замер естественного цикла.
- **Воспроизведение полного естественного цикла без SQL (R6)** — N1 и N10, K операций, тот же планировщик A5:
  - накопление прогонов, слияния ярусов шагами, раунд с W;
  - шаги прохода заменены чтением ключей из памяти, страницы случайные, как в A4.
  - Измеряется максимум **суммарной работы границы** без прохода PostgreSQL, отдельно — границы, где совпали
    запечатывание, шаг слияния и шаг раунда.
  - Пределы этого свидетельства: проход PostgreSQL в нём не участвует, его цена берётся из замеров раундов.
- **Дешёвый опыт по рабочему файлу (описательно):** одна реальная секция рабочего файла N1 сжимается `zlib` уровня 6
  без потерь. Сообщаются размер, время и точность восстановления.

Три исхода: ПРОХОДИТ, НЕ ПРОХОДИТ (критерий), НЕ УСТАНОВЛЕНО (ошибка реализации или незавершённый прогон).

- **H-A5 ПРОХОДИТ**, если выполнены все условия:
  - **S0, правильность:** 0 ошибок C4 во всех точках на N1 и N10; 0 ошибок применения; все сценарии верны; все
    свидетели верны; мутанты (а)–(л) пойманы.
  - **S1, обслуживание:** установившаяся стоимость на операцию (§5) на N10 ≤ 1,5 × той же на N1 — по времени и по
    логическому объёму (как A4). На N10 — условная оценка (R8).
  - **S2, поиск:** среднее обращений на запрос живого ключа ≤ того же у B-tree-контроля в каждой точке на N1 и N10.
  - **S3, байты:** опубликованная основная структура (включая закреплённые входы и готовые секции выхода активного
    слияния) ≤ 8,0 байта на живой ключ в каждой точке C4 и на каждой границе пакета, на N1 и N10.
  - **S4, паузы обслуживания адреса (новое, главное):**
    - максимальная пауза границы пакета в рабочем режиме ≤ 1,0 с на N1 и на N10 (прогоны с PostgreSQL);
    - максимальная пауза на N10 ≤ 1,5 × максимальной на N1;
    - в воспроизведении естественного цикла N10 максимальная суммарная работа границы ≤ 1,0 с.
    - Критерий — максимум, а не p99, потому что p99 может скрыть редкую длинную паузу (R6).
- **Формулировка вердикта** — «критерии адресного слоя». Рядом стоят:
  - общая эффективность (полная стоимость на операцию, общая максимальная остановка клиентов);
  - пик файлов адресного слоя с рабочими файлами раунда — отдельный показатель без порога.

## 7. Прогноз (до кода)

- **Обращения:** A5 1,00–1,05, контроль 4,0, как в A4.
- **Пауза границы пакета:**
  - N1: шаг прохода около 2,1 / 8 ≈ 0,26 с плюс накладные Python → максимум 0,3–0,5 с;
  - N10: шаг прохода около 13,6 / 128 ≈ 0,11 с, шаг построения около 4,9 / 128 ≈ 0,04 с, шаг слияния около
    σ записей ≈ 0,1–0,2 с, совпадения на одной границе до суммы → максимум 0,2–0,5 с;
  - отношение N10/N1 около 0,5–1,3. S4 выполняется;
  - финальный раунд подряд: около суммы раунда A4 × 1,1–1,4.
- **Установившееся обслуживание:** раунд в 1,1–1,4 раза дороже большого слияния A4 (накладные на срез, рабочие
  файлы). N1 около 28–38 мкс на операцию, N10 около 24–32; отношение 0,7–1,1.
- **Байты:**
  - пик основной структуры N1 5,5–6,8 (дельта живёт дольше на окно раунда, около 16 пакетов, плюс закреплённые
    входы), N10 4,3–5,2;
  - рабочие файлы — около 20 байт на живой ключ в пике раунда (полный набор ключей). Это больше всей основной
    структуры, но только на время окна: N1 около 16 пакетов из 100, N10 около 256 пакетов на раунд;
  - сжатие `zlib` почти ничего не даст: ключи случайны (около 0,95–1,0 исходного размера).
- **Полная стоимость на операцию** — как в A4 ±10%: около 1,2 раза дороже B-tree на N1, около паритета на N10.
- **P(H-A5 ПРОХОДИТ) ≈ 50%.** Риски:
  - S0: новый код шагов, смешанные поколения, приоритеты;
  - S4: накладные Python на шаг, GC, совпадение работ на одной границе;
  - S3 на N1 из-за закреплённых входов.

## 8. Границы

- Контракт A4 (единственный писатель, сериализация, обслуживание при остановленных клиентах) и предпосылка §2.
  Шаги — модель инкрементальной работы, а не фоновый процесс.
- S1 и S4 подтверждают ограниченные отношения на двух размерах в одном прогоне, а не асимптотику и не
  гарантированный предел задержки. S4 ограничивает паузы обслуживания адреса, а не все остановки клиентов.
- **Рабочие файлы раунда — полный временный список «ключ → страница».** Для поиска он не используется и в основную
  структуру не входит, но это вспомогательное отображение размером больше самой структуры. Совместимо ли оно с
  ограничением владельца «без скрытого индекса» — решает владелец. Отчёт выносит этот вопрос явно.
- Смена S_base (рост N в разы) не делается: это раунд с перегруппировкой в другое число секций.
- Python-клиент, тёплый кэш ОС, одна машина, настройки PostgreSQL по умолчанию, синтетический корпус.
- Только точечный поиск. Новизна принципа не утверждается: это известный приём LSM — разбиение уплотнения на
  подзадачи по диапазонам ключей (subcompactions). Из него взяты правила закрепления входов, порядка версий и
  публикации частей.

## 9. Рассмотренные альтернативы (не выбраны)

1. **Срезы базы по диапазонам страниц, а не по хешу.** Рабочего файла нет, но ключ не знает своего среза. Поиск
   пробует все S срезов, и число пробников растёт как S ∝ N — масштабирование поиска теряется.
2. **Обновление значений статической функции на месте.** Требует точного признака принадлежности ключа базе: короткий
   отпечаток не годится, чтобы разрешить запись в слот. Вставки всё равно копятся. Откладывает раунд, но не убирает.
3. **Рабочий файл только с хешем (12 байт).** Не отличить повтор ключа от коллизии 64-битного хеша, а исключениям
   JLMADR01 нужен полный ключ. Не выбрано ради правильности.
4. **Несколько проходов группами секций.** Рабочий файл делится на G, а чтение умножается на G. Не делается в A5.
5. **Хеш-партиционирование самой таблицы.** Тогда «страницы секции» существуют, и перегруппировка не нужна. Но это
   меняет физическую организацию таблицы и условия сравнения с контролем. Отдельный опыт, назван следующим шагом.

## 10. Ресурсы и порядок

- Диск: как в A4 (N10 — две таблицы около 6,3 ГБ, B-tree 0,3 ГБ) плюс рабочие файлы около 0,2 ГБ. Свободно 32 ГБ.
- Время: самопроверка и N1 около 1 ч, N10 около 2,5 ч (загрузка контрольной таблицы в A4 шла 81 мин),
  воспроизведения около 15 мин.
- Порядок: самопроверка и сценарии → N1 → N10 → воспроизведения → отчёт `a5_report.md`. Ошибка правильности на любом
  шаге — стоп, исправление, повтор с раскрытием.
