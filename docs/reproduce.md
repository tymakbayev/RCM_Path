# Повторение экспериментов A2-A8

Для первого знакомства достаточно [демо](../README.md#быстрый-запуск). Ниже описан полный повтор экспериментов из
[`experiments/`](experiments/), сведённых в [`results.md`](results.md).

## Требования

- PostgreSQL 18 (проверено на 18.7) в виде отдельного локального тестового кластера.
  - Скрипты перезапускают кластер через `pg_ctl` для проверок холодного старта. `pg_ctl` выполняется под учётной
    записью ОС, которой принадлежит кластер, и не под root; роль суперпользователя PostgreSQL этих прав не даёт.
  - Скрипты создают и удаляют таблицы в базе `a2` и устанавливают расширения `pageinspect`, `pg_buffercache` и
    `pg_prewarm`, поэтому роль должна быть суперпользователем.
  - Перед замерами проверяется, что SQL-подключение ведёт к кластеру из `RCM_PG_DATA`.

  Сервер с рабочими данными для этого не подходит.
- Python 3.10+ и `pip install -r requirements.txt` (numpy 2.2.6 и psycopg 3.2.10, версии эталонных прогонов; от версии
  numpy зависят случайные потоки генератора).
- Диск на томе с данными. A7 и A8 на 10M перед стартом проверяют наличие не менее 24 ГБ свободного места (три таблицы
  по 6,4 ГБ). Ориентировочно: прогонам 1M достаточно нескольких ГБ; таблицы статики A2 на 10M заняли около 13 ГБ.
- Память: на эталонном стенде 32 ГБ. Пиковый RSS процесса Python 4,4 ГБ (A7, 10M) и 5,18 ГБ (A6, 10M, с эталонной
  моделью).
- Время по меткам в логах эталонных прогонов, ориентировочно: самопроверка 2-20 мин, динамика 1M около 15 мин,
  динамика 10M 1-2 ч, статика A2 на 10M 30 мин.

## Настройка стенда

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `RCM_PG_DATA` (или `PGDATA`) | каталог данных тестового кластера: рестарты, проверка места и кластера; для демо не нужен | нет |
| `RCM_PG_BIN` | каталог с `pg_ctl` | каталог `pg_ctl` из `PATH` |
| `RCM_PG_LOG` | журнал сервера для `pg_ctl -l` (при нехватке места на долгих прогонах выносится с тома данных) | `$RCM_PG_DATA/rcm_server.log` |
| `PGHOST`, `PGPORT`, `PGUSER` | подключение к тому же кластеру | `localhost`, `5432`, `postgres` |
| `PGPASSWORD` или `RCM_PG_PWFILE` | пароль или файл с паролем (`~/.pgpass` libpq тоже работает) | нет |
| `RCM_DB` | база для таблиц экспериментов и демо | `a2` |

На эталонном стенде использовались порт 5433 и роль-суперпользователь `bench`. Счётчики устройства в Windows (A8)
берутся по букве диска из `RCM_PG_DATA`; для каталога данных на томе, смонтированном в папку, за junction или на
сетевом пути, собственный том не определяется.

## Шаги

```sh
cd rcm_address_engine

# без базы
python verify_corpus.py small         # побитное воспроизведение эталонных массивов (также n1, n10)
python a2_selftest_core.py            # ядро адреса
python a5_selftest_lsm.py             # LSM адресов, слияние шагами, рестарты посреди раунда
python a6_selftest_lsm.py             # вариант «шаг слияния равен партиции»
python prepare_data.py                # data/dyn.copy: поток вставок для A2 dynamics, A3 и A4-A8 (2-3 мин)
python prepare_data.py --replay       # файлы для replay в A5 и A6 (ещё около 4 мин)

# с тестовым кластером (измеряемые величины описаны в протоколе каждого эксперимента)
python a2.py selfcheck ; python a2.py static N1 ; python a2.py static N10 ; python a2.py dynamics
python a2.py dynamics-a3
python a4_run.py selfcheck ; python a4_run.py dynamics N1 ; python a4_run.py dynamics N10 ; python a4_run.py replay N1
python a5_run.py selfcheck ; python a5_run.py dynamics N1 ; python a5_run.py dynamics N10 ; python a5_run.py replay N1
python a6_run.py selfcheck ; python a6_run.py dynamics N1 ; python a6_run.py dynamics N10 ; python a6_run.py replay N10
python a7_run.py selfcheck ; python a7_run.py dynamics N1 r1 ; python a7_run.py dynamics N10 r1
python a8_run.py selfcheck ; python a8_run.py run
```

- Эксперименты запускаются по одному: часть из них перезапускает сервер.
- A6-A8 выполняют динамику только после успешной самопроверки той же версии кода на этом стенде. Файлы самопроверки
  эталонного стенда в `results/` не засчитываются: хеш кода изменился при подготовке к публикации.
- Результаты записываются в [`results/`](../results/README.md) поверх эталонных с теми же именами файлов; при работе в
  отдельной ветке `git diff` показывает расхождения с эталоном.
- Код для Linux написан, но с PostgreSQL на Linux не запускался.

## Проверка после подготовки к публикации

Для публикации код экспериментов сделан переносимым: настройки из переменных окружения, автономный генератор,
счётчики для Linux, новая раскладка папок. Алгоритмы не менялись. Проверка на PostgreSQL 18.7 (zip-сборка EDB):

- самопроверки A2, A4, A5, A6, A7 и A8 пройдены (`all_ok: true`) дважды: до перестановки папок и на итоговой
  раскладке. Самопроверка A2 оба раза совпала с эталонной (`results/a2_selfcheck.json`) по всем полям;
- `prepare_data.py` воссоздал входной поток вставок, все четыре файла побитно совпали с файлами прогонов;
- `rcm_pgtest.py` пройден под суперпользователем и под обычной ролью, демо выполнено на 5 000 и 200 000 строк
  ([`results/demo_reference_*.json`](../results/README.md)).

Длинные прогоны на 1M и 10M после переноса не повторялись, их результаты лежат в `results/`. Самопроверки
подтверждают предусмотренные ими сценарии и мутанты, но не эквивалентность всего поведения, включая
производительность.

## Воспроизводимость данных

`corpus.py` является дословной копией генератора автора из проекта JARVIS-LM. На эталонном стенде массивы ключей,
дайджестов и длин записей, которые он выдаёт, побитно совпали с массивами опубликованных прогонов для 100 тыс., 1 млн
и 10 млн записей (`verify_corpus.py`). Текстовый поток COPY, подаваемый в PostgreSQL, побитно совпал с исходным
генератором на сравненных участках. Проверено на Windows.

## История кода

Первый коммит содержит файлы экспериментов в том виде, в каком шли прогоны. Последующие коммиты делают их
переносимыми и добавляют API, демо и тесты; подробности в описаниях коммитов. Комментарии в коде экспериментов на
английском языке, так как файлы публикуются в исходном виде.
