# Как повторить эксперименты A2–A8

Для знакомства хватит [демо](../README.md#попробовать-за-несколько-минут). Здесь — полный повтор экспериментов,
которые описаны в [`experiments/`](experiments/) и сведены в [`results.md`](results.md).

## Что нужно

- **PostgreSQL 18** (проверено на 18.7): **отдельный локальный тестовый кластер**, которым вы управляете.
  - Скрипты запуска перезапускают его через `pg_ctl` для проверок холодного старта. `pg_ctl` должен работать под учётной
    записью ОС, которой принадлежит кластер, и не под root. Роль-суперпользователь PostgreSQL этих прав не даёт.
  - Они создают и удаляют таблицы в базе `a2` и создают расширения `pageinspect`, `pg_buffercache` и `pg_prewarm`,
    поэтому роль должна быть суперпользователем.
  - Перед любым замером они проверяют, что SQL-подключение ведёт к кластеру из `RCM_PG_DATA`.

  Не направляйте их на сервер с нужными данными.
- **Python 3.10+** и `pip install -r requirements.txt` (numpy 2.2.6 и psycopg 3.2.10 — версии эталонных прогонов;
  numpy задаёт случайные потоки генератора).
- **Диск** на томе с данными. A7 и A8 на 10M проверяют перед стартом, что свободно не меньше 24 ГБ (три таблицы по
  6,4 ГБ). Ориентировочно: прогонам 1M хватит нескольких ГБ, таблицы статики A2 на 10M заняли около 13 ГБ.
- **Память**: на эталонном стенде 32 ГБ. Пиковый RSS процесса Python — 4,4 ГБ (A7, 10M) и 5,18 ГБ (A6, 10M, с
  эталонной моделью).
- **Время**, ориентировочно, по меткам времени в логах эталонных прогонов: самопроверка 2–20 мин, динамика 1M около
  15 мин, динамика 10M 1–2 ч, статика A2 на 10M — 30 мин.

## Настройка стенда

| Переменная | Значение | По умолчанию |
|---|---|---|
| `RCM_PG_DATA` (или `PGDATA`) | каталог данных тестового кластера (рестарты, проверка места, проверка кластера); демо не нужен | нет |
| `RCM_PG_BIN` | каталог с `pg_ctl` | каталог `pg_ctl` из `PATH` |
| `RCM_PG_LOG` | журнал сервера для `pg_ctl -l` (при нехватке места на долгих прогонах вынесите его с тома данных) | `$RCM_PG_DATA/rcm_server.log` |
| `PGHOST`, `PGPORT`, `PGUSER` | подключение к тому же кластеру | `localhost`, `5432`, `postgres` |
| `PGPASSWORD` или `RCM_PG_PWFILE` | пароль или файл с ним (работает и `~/.pgpass` libpq) | нет |
| `RCM_DB` | база для таблиц экспериментов и демо | `a2` |

На эталонном стенде были порт 5433 и роль-суперпользователь `bench`. Счётчики устройства в Windows (A8) берутся по
букве диска из `RCM_PG_DATA`. Если каталог данных лежит на томе, смонтированном в папку, за junction или на сетевом
пути, его собственный том не определяется.

## Шаги

```sh
cd rcm_address_engine

# без базы
python verify_corpus.py small         # эталонные массивы воспроизводятся побитно (ещё: n1, n10)
python a2_selftest_core.py            # ядро адреса
python a5_selftest_lsm.py             # LSM адресов со слиянием шагами и рестартами посреди раунда
python a6_selftest_lsm.py             # вариант «шаг — партиция»
python prepare_data.py                # data/dyn.copy: поток вставок для A2 dynamics, A3 и A4–A8 (около 2–3 мин)
python prepare_data.py --replay       # плюс файлы для replay в A5 и A6 (ещё около 4 мин)

# с настроенным тестовым кластером (что именно измеряется — в протоколе каждого эксперимента)
python a2.py selfcheck ; python a2.py static N1 ; python a2.py static N10 ; python a2.py dynamics
python a2.py dynamics-a3
python a4_run.py selfcheck ; python a4_run.py dynamics N1 ; python a4_run.py dynamics N10 ; python a4_run.py replay N1
python a5_run.py selfcheck ; python a5_run.py dynamics N1 ; python a5_run.py dynamics N10 ; python a5_run.py replay N1
python a6_run.py selfcheck ; python a6_run.py dynamics N1 ; python a6_run.py dynamics N10 ; python a6_run.py replay N10
python a7_run.py selfcheck ; python a7_run.py dynamics N1 r1 ; python a7_run.py dynamics N10 r1
python a8_run.py selfcheck ; python a8_run.py run
```

- Запускайте эксперименты **по одному**: часть из них перезапускает сервер.
- A6–A8 не запустят динамику, пока на вашем стенде не пройдёт самопроверка ровно этой версии кода. Файлы
  самопроверки эталонного стенда в `results/` не засчитываются: хеш кода изменился при подготовке к публикации.
- Результаты пишутся в [`results/`](../results/README.md) поверх наших, с теми же именами файлов. Работайте в
  отдельной ветке или скопируйте папку заранее; тогда `git diff` покажет ваши числа рядом с нашими.
- Ветки кода для Linux написаны, но с PostgreSQL там ещё не запускались.

## Что проверено после подготовки к публикации

Для публикации код экспериментов сделан переносимым: настройки из переменных окружения, автономный генератор,
счётчики для Linux, новая раскладка папок. Алгоритмы не менялись. После этого на PostgreSQL 18.7 (zip-сборка EDB):

- самопроверки A2, A4, A5, A6, A7 и A8 прошли (`all_ok: true`); самопроверка A2 совпала с эталонной
  (`results/a2_selfcheck.json`) по всем полям;
- `prepare_data.py` воссоздал входной поток вставок, и все четыре файла побитно совпали с файлами прогонов.

Длинные прогоны на 1M и 10M после переноса не повторялись: их результаты — в `results/`. Самопроверки прошли на
предусмотренных ими сценариях и мутантах; эквивалентность всего поведения, включая производительность, они не
доказывают.

## Воспроизводимые данные

`corpus.py` — дословная копия генератора автора (из проекта JARVIS-LM). На эталонном стенде массивы ключей,
дайджестов и длин записей, которые он выдаёт, побитно совпали с массивами опубликованных прогонов для 100 тыс.,
1 млн и 10 млн записей (`verify_corpus.py`). Текстовый поток COPY, который подаётся в PostgreSQL, тоже побитно совпал
с исходным генератором на сравненных окнах. Проверено только на Windows.

## История кода

В первом коммите файлы экспериментов лежат ровно в том виде, в каком они работали. Следующие коммиты делают их
переносимыми и добавляют API, демо и тесты; подробности — в описаниях коммитов. Комментарии в коде экспериментов
написаны по-английски — файлы публикуются в том виде, в каком шли прогоны.
