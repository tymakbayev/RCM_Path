# История идеи

## Исходная задача: компактная долговременная память

RCM Path начинался как часть проекта JARVIS-LM, долговременной памяти локального голосового ассистента. Название
означает Reconstructive Compact Memory: запись хранится не целиком, а как генератор, траектория (путь) и остаток,
x̂ = Unfold_G(p) ⊕ r. Модель и её проверка описаны в [`theory/`](theory/README.md).

С сентября по октябрь 2026 года модель проверялась серией экспериментов E1-E23 по сжатию данных без потерь:

- E17: языковая модель как генератор, 1,39 бита на символ на корпусе диалогов (5 797 байт), коэффициент сжатия 10,1×;
- E19: каскад сжатия на корпусе из 47 499 наблюдений (133 984 факта), 11,5× относительно явного представления
  обязательных данных;
- E20: тот же каскад внутри работающего движка памяти, 10,74× с побайтным восстановлением после перезапуска.

## Наблюдение: индекс съедает выигрыш

В E19 обнаружилось, что поисковый индекс становится главной статьёй расхода. Если хранить индекс по 16 байт на
объект, коэффициент сжатия падает с 11,5× до 3,5×. Вывод модели (`memory_math.md` §19.2c): индекс поиска выгоднее
выводить из данных, чем хранить.

Отсюда вопрос, с которого начался адресный движок: если содержимое восстанавливается по генератору и пути, нельзя ли
так же вычислять местоположение записи по её ключу, вместо того чтобы хранить привычную индексную структуру?

## Этап 1: схема и граница (16 ноября 2026)

Аудит ([`STAGE1_postgresql_branch.md`](experiments/STAGE1_postgresql_branch.md)) перевёл вопрос в конкретную схему:

- ключ хешируется; каскад битовых карт (минимальная совершенная хеш-функция) даёт ячейку; в ячейке хранятся
  8-битный отпечаток и номер страницы;
- информационная граница: при размещении, не связанном с ключом, номер страницы требует около log2(число страниц)
  бит на запись, и эта часть неустранима;
- оценка: 3,0-3,5 байта на запись против 21-31 байта у B-tree в замере на SQLite.

В тот же день принято решение не строить собственную СУБД, а подключить адресацию к PostgreSQL как внешний модуль:
таблица, транзакции и хранение остаются у PostgreSQL, движок отвечает только за вычисление страницы.

## Эксперименты A2-A8 (16-17 ноября 2026)

Каждый шаг отвечал на ограничение, найденное предыдущим:

| Эксперимент | Вопрос | Результат |
|---|---|---|
| A2 | работает ли вычисляемый адрес рядом с таблицей PostgreSQL | адрес в 8-9 раз меньше B-tree, поиск читает одну страницу, 0 неверных ответов; дельта изменений в частичном B-tree дорожает |
| A3 | можно ли держать дельту малой частой пересборкой | да, 3,0 обращения против 4,0; цена пересборки растёт с размером таблицы |
| A4 | можно ли обойтись без полной пересборки | уровни маленьких адресов с ярусными слияниями: 1,00-1,04 обращения против 4,0, цена обслуживания на 10M ниже, чем на 1M |
| A5 | можно ли разбить большое слияние на шаги | самая длинная пауза на 10M сократилась с 18,5 до 0,40 с |
| A6 | можно ли убрать рабочий файл слияния | шаг слияния равен хеш-партиции таблицы: пауза 0,62 / 0,36 с, рабочий файл не нужен |
| A7 | сколько стоит само партиционирование | на 1M ×1,23-1,25 по времени операций; на 10M в совместном прогоне знак обратный |
| A8 | почему в A7 на 10M одиночная таблица замедлилась | протокол, код и самопроверка готовы; прогон на 10M ожидает стенда с большим диском |

Порядок работы описан в [`method/`](method/README.md): протокол фиксируется до прогона, каждый шаг проверяется на
сценариях с намеренно внесёнными ошибками, результат принимается по измерению.

## Публикация (ноябрь 2026)

Для публикации код сделан переносимым, добавлены API для собственной таблицы и демо. Генератор данных воспроизводит
наборы экспериментов побитно. Все самопроверки повторно пройдены на PostgreSQL 18.7. Дальнейшие вопросы, требующие
более мощного стенда, перечислены в README в разделе «Независимая проверка».
