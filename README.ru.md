# RCM Path: вычисляемый адресный слой для PostgreSQL

**RCM Address Engine** находит страницу кучи PostgreSQL, на которой лежит строка, **вычисляя** её по ключу, а не
обходя B-tree. На ключ уходит около **3–5 байт**: каскад минимальной совершенной хеш-функции, отпечаток 8 бит и номер
страницы. У B-tree PostgreSQL на тот же ключ — около 31,5 байта. Движок работает как **sidecar** рядом с обычной
таблицей PostgreSQL: своей СУБД нет, сервер не патчится. Поиск существующего ключа читает одну страницу кучи через
Tid Range Scan и проверяет ключ.

Репозиторий — полная воспроизводимая запись экспериментов **A2–A8** (ноябрь 2026). Идея проверялась на **1 и
10 млн строк**: статически и под потоком вставок, обновлений и удалений. Здесь:

- код;
- протоколы, зафиксированные по sha256 до измерительных прогонов;
- сырые результаты и отчёты.

Все числа получены на одном скромном настольном компьютере, результаты предварительные. Публикуем, чтобы другие
могли **повторить эксперименты на более сильном железе** и на больших N, а также продолжить их. Что именно нужно —
в разделе [«Что просим проверить»](#что-просим-проверить).

## Как это работает

```
ключ (uuid, 16 Б) ──hash64(ключ, зерно)──► h                      G  порождается, не хранится
h ──► P: каскад битовых карт «ключ попал в ячейку один»             P  ≈3 бита на ключ, ранг за O(1)  ──► slot
slot ──► D[slot] = отпечаток (8 бит) | страница кучи (⌈log2 страниц⌉ бит)   R  остаток на ключ
SELECT … FROM t WHERE ctid >= '(page,0)' AND ctid < '(page+1,0)' AND k = $key    читает эту страницу кучи
```

- **Статический адрес не хранит ни ключей, ни дерева поиска.** Адресный файл (формат `JLMADR01`) — плоские массивы,
  и время его открытия от N не зависит.
- **Возвращённая строка — всегда запрошенный ключ.** Ключ сравнивается в самой строке. Совпадение отпечатка стоит
  одного лишнего чтения страницы, но не чужой строки. Отсутствующие ключи почти всегда отсеиваются по отпечатку ещё до
  SQL. Чтобы находилась каждая живая строка, адрес должен идти в ногу с таблицей — это обеспечивают
  [условия работы прототипа](#условия-работы-прототипа).
- **Изменяющиеся данные (A4–A6).**
  - Новые строки идут в журнал хвоста. Запечатанные пакеты становятся маленькими адресами («прогонами»), а прогоны
    сливаются ярусами, как LSM-дерево из адресов.
  - Эти варианты хранят ещё и журналы прогонов с полными ключами (ключ 16 Б + страница 4 Б) для слияний. На пути
    поиска журналы не участвуют.
  - Большое слияние идёт ограниченными шагами: по хеш-секциям адреса (A5) или по хеш-партициям таблицы (A6).
- **Только точечный поиск по ключу.** Диапазоны и порядок по-прежнему требуют B-tree.
- **Это всё равно индекс** — статическая функция «ключ → страница», а не «индекс в 0 байт». Если место строки не
  зависит от ключа, точное отображение «ключ → страница» стоит около log2(число страниц) бит на строку, а «ключ →
  позиция строки» — около log2(n) − 1,44 бита (`rcm_address_engine/STAGE1.md` §2.1). Поле страницы выше — это и есть
  неустранимая часть. Каскад (≈3 бита) и отпечаток (8 бит) — накладные расходы.

Идея выросла из модели RCM Path «генератор + траектория + остаток», которую автор сначала строил для компактной
долговременной памяти: [`theory/`](theory/README.md).

### Что установлено и что нет

Установлено на 1 и 10 млн строк, на одной машине:

- статический вычисляемый адрес примерно в 8–9 раз меньше B-tree PostgreSQL на том же ключе. Поиск существующего
  ключа читает ровно одну страницу кучи, а отсутствующие ключи почти никогда не доходят до таблицы;
- под смешанным потоком из 500 000 записей адрес держит ≈1 обращение к буферам PostgreSQL на поиск живого ключа
  против 4, без неверных ответов в предусмотренных проверках;
- монолитной паузы пересборки нет: базовый адрес обновляется по секциям (A5) или по партициям (A6). Измеренные
  паузы и расчётная цена обслуживания на операцию на 10M были ниже, чем на 1M.

Не установлено или отрицательно:

- **Выигрыша по задержке нет.** Меньше обращений к буферам не ускорило запросы при тёплом кэше. И серверная часть, и
  клиент на Python медленнее Index Scan по B-tree. Реализация поиска на C (например, как метод доступа индекса
  PostgreSQL) не делалась.
- **Полная стоимость операции в A4–A6 не лучше B-tree**: на 1M выше (×1,09–1,39), на 10M примерно наравне
  (×0,995–1,05). A7 намерил ×0,853 на 10M, но только при совместной работе трёх таблиц, где одиночная таблица
  замедлилась по неизвестной причине. Сравнение отдельно работающих систем открыто; для этого задуман A8. Его
  протокол, код и самопроверка готовы, но прогон на 10M не сделан — на стенде кончилось место на диске.
- **Масштаб.** Проверены только два размера. У A4–A6 по одному прогону на размер; у A7 два прогона на 1M и один на
  10M. На 100M ничего не запускалось. Для A6 там понадобится переразбивка таблицы (около 1 024 партиций, вывод),
  она не проверялась.
- **Отрицательные вердикты протоколов** оставлены как есть:
  - A2 не прошёл критерий A4b. Вариант А превысил число обращений к буферам у контроля B-tree в двух точках
    (4,019 / 4,004 против 4,013 / 4,000); вариант Б — во всех 12 (4,25–5,12 против 4,00).
  - A5 не уложился в собственный порог паузы 1,0 с на 1M (1,13 с).

### Условия работы прототипа

Гарантии выше действуют только при этих условиях:

- один писатель; читатели сериализованы с пакетами записи; обслуживание идёт, пока клиенты ждут (это и есть
  измеренная пауза);
- без длительных снимков и без `VACUUM FULL` и `CLUSTER`: они перемещают строки и сделали бы адреса неверными;
- только согласованные рестарты между пакетами. Сбой ОС вне контракта.
- Это sidecar, а не метод доступа индекса PostgreSQL. WAL и восстановление после сбоя PostgreSQL адресные файлы не
  покрывают.

Что учитывается, а что нет:

- «Байт адреса» — опубликованный адрес. Временные файлы слияний и память процесса показаны отдельно: пиковый RSS
  клиента на Python в A6 — 1,17 / 5,18 ГБ вместе с эталонной моделью проверки и 134 / 893 МБ у воспроизведения без
  SQL.
- «Обращения к буферам» — только буферы PostgreSQL. Чтение адреса и работа Python сюда не входят, и это не число
  физических чтений с SSD.

Как велась работа:

- У каждого эксперимента протокол зафиксирован по sha256 до измерительных прогонов; факты, найденные позже, — в
  датированных приложениях. Хеши лежат в `rcm_address_engine/results/*_protocol.sha256`, и каждый запускатор
  отказывается работать, если его протокол изменился.
- Числа в отчётах помечены: ЗАМЕР, ВЫВОД или ИСТОЧНИК (взято из другого прогона).
- Исследовательская гипотеза излагается отдельно от вердиктов протокола.

и приложениях. Сам метод (Assume → Build → Break; модели предлагают, человек направляет, эксперимент решает) описан в
эссе автора: [`docs/`](docs/README.md).

## Как запустить у себя

### Что нужно

- **PostgreSQL 18** (проверено на 18.7): **отдельный локальный тестовый кластер**, которым вы управляете.
  - Запускаторы перезапускают его через `pg_ctl` для проверок холодного старта. `pg_ctl` должен работать под учётной
    записью ОС, которой принадлежит кластер, и не под root. Роль-суперпользователь PostgreSQL этих прав не даёт.
  - Они создают и удаляют таблицы в базе `a2` и создают расширения `pageinspect`, `pg_buffercache` и `pg_prewarm`,
    поэтому роль должна быть суперпользователем.
  - Перед любым замером они проверяют, что SQL-подключение ведёт к кластеру из `RCM_PG_DATA`.

  Не направляйте их на сервер с нужными данными.
- **Python 3.10+** и `pip install -r requirements.txt` (numpy 2.2.6 и psycopg 3.2.10 — версии эталонных прогонов;
  numpy задаёт случайные потоки генератора).
- **Диск** на томе с данными. A7 и A8 на 10M проверяют перед стартом, что свободно не меньше 24 ГБ (три таблицы по
  6,4 ГБ). Ориентировочно: прогонам 1M хватит нескольких ГБ, таблицы статики A2 на 10M заняли около 13 ГБ.
- **Память**: на эталонном стенде 32 ГБ. Пиковый RSS процесса Python — 4,4 ГБ (A7, 10M) и 5,18 ГБ (A6, 10M, с
  эталонной моделью).
- **Время**, ориентировочно, по меткам времени в логах эталонных прогонов: самопроверка 5–10 мин, динамика 1M около
  15 мин, динамика 10M 1–2 ч, статика A2 на 10M — 30 мин.

| `RCM_PG_DATA` (или `PGDATA`) | каталог данных тестового кластера (рестарты, проверка места, проверка кластера) | нет |
| `RCM_PG_BIN` | каталог с `pg_ctl` | каталог `pg_ctl` из `PATH` |
| `RCM_PG_LOG` | журнал сервера для `pg_ctl -l` (при нехватке места на долгих прогонах вынесите его с тома данных) | `$RCM_PG_DATA/rcm_server.log` |
| `PGHOST`, `PGPORT`, `PGUSER` | подключение к тому же кластеру | `localhost`, `5432`, `postgres` |
| `PGPASSWORD` или `RCM_PG_PWFILE` | пароль или файл с ним (работает и `~/.pgpass` libpq) | нет |
| `RCM_DB` | база для таблиц экспериментов | `a2` |

На эталонном стенде были порт 5433 и роль-суперпользователь `bench`. Счётчики устройства в Windows (A8) берутся по
букве диска из `RCM_PG_DATA`. Если каталог данных лежит на томе, смонтированном в папку, за junction или на сетевом
пути, его собственный том не определяется.

### Шаги

```sh
python -m venv .venv
. .venv/bin/activate                  # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cd rcm_address_engine

# без базы
python verify_corpus.py small         # эталонные массивы воспроизводятся побитно (ещё: n1, n10)
python a2_selftest_core.py            # ядро адреса
python a5_selftest_lsm.py             # LSM адресов со слиянием шагами и рестартами посреди раунда
python a6_selftest_lsm.py             # вариант «шаг — партиция»

# с настроенным тестовым кластером (что именно измеряется — в протоколе каждого эксперимента)
python a2.py selfcheck ; python a2.py static N1 ; python a2.py static N10 ; python a2.py dynamics
python a2.py dynamics-a3
python a4_run.py selfcheck ; python a4_run.py dynamics N1 ; python a4_run.py dynamics N10 ; python a4_run.py replay N1
python a5_run.py selfcheck ; python a5_run.py dynamics N1 ; python a5_run.py dynamics N10 ; python a5_run.py replay N1
python a6_run.py selfcheck ; python a6_run.py dynamics N1 ; python a6_run.py dynamics N10 ; python a6_run.py replay N10
python a7_run.py selfcheck ; python a7_run.py dynamics N1 r1 ; python a7_run.py dynamics N10 r1
python a8_run.py selfcheck ; python a8_run.py run
```

- Запускайте эксперименты **по одному**: часть из них перезапускает сервер.
- A6–A8 не запустят динамику, пока на вашем стенде не пройдёт самопроверка ровно этой версии кода. Файлы
  самопроверки эталонного стенда в `results/` не засчитываются: хеш кода изменился в коммитах переносимости.
- Результаты пишутся в `rcm_address_engine/results/` поверх наших, с теми же именами файлов. Работайте в отдельной
  ветке или скопируйте папку заранее; тогда `git diff` покажет ваши числа рядом с нашими.
- Ветки кода для Linux написаны, но с PostgreSQL там ещё не запускались.

## Что просим проверить

У нас один настольный компьютер, поэтому открыты такие вопросы:

1. **A8 на 10M**: почему поиск существующего ключа в одиночной таблице вдвое медленнее, когда три таблицы по 6,4 ГБ
   делят один сервер? Нужно ≥ 24 ГБ свободного диска. Больше памяти или быстрый NVMe — только лучше; укажите их в
   отчёте.
2. **A6 и A7 на 10M и на больших N** (например, 100M): остаются ли ровными цена обслуживания на операцию и самая
   длинная пауза? Та же ли цена партиционирования, когда каждая система работает одна?
3. **Другое железо и настройки**: Linux, NVMe, больший `shared_buffers`.
4. **Поиск на C** (метод доступа индекса или C-расширение): может ли адрес с одной страницей обогнать B-tree по
   задержке, а не только по байтам и обращениям.

Чтобы поделиться результатами, откройте issue по шаблону **Results** и приложите:

- файлы JSON и логи из `results/`;
- процессор, память и накопитель;
- ОС, версию и настройки PostgreSQL. Результаты A2, A7 и A8 записывают настройки сами; для остальных приложите вывод
  `SHOW ALL`.
