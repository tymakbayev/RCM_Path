# A2 — протокол этапа 2: точечный поиск по ключу без B-дерева (варианты А и Б)

Редакция 1 (черновик до Codex), 2026-11-16. После ответа Codex — редакция 2, sha256 в `results/a2_protocol.sha256`,
дальше файл не меняется; поздние факты — в датированные приложения. Метки чисел: ЗАМЕР, ВЫВОД, ИСТОЧНИК.
Основание: `STAGE1.md` (аудит, граница log2(n!)/n, черновик JLMADR01). Решение владельца 2026-11-16: «Берём оба
варианта». Код — только в `rcm_address_engine/`; существующий код движка не меняется, импортируется только для
генерации корпуса (`experiments/e19_cascade.py`, `e20_engine_cascade.py`, `jarvis_mem.engine.deletion.memory_id`).
GPU не используется. Стенд владельца (:8089) не затрагивается.

## 1. Вопросы

- **H-A.** Вариант А (порядок поступления, совершенная хеш-функция P + дескриптор R = отпечаток и номер блока, mmap):
  даёт ли он 100% правильных ответов при ≤ 8 байт адресных метаданных на запись на 1 млн и 10 млн записей, открытие
  без зависимости от N и устойчивость к INSERT / UPDATE / DELETE без полной перестройки?
- **H-Б.** Вариант Б (место записи в сегменте порождается хешем ключа, P = R = 0, фильтр сегмента): насколько он
  меньше по метаданным, сколько стоит по сжатию полезных данных и меньше ли он варианта А по ПОЛНОМУ объёму
  (данные + адресные метаданные)?

## 2. Данные

- Поток записей: копии корпуса E19/E20 (тот же генератор, что в E21). Копия k (k = 0, 1, …) строится
  `e19.build_corpus(2026 + k, 0.0)` при `e19.TIME_UNIT_MS = 1`, затем `e20.to_observations`; эпоха `e{k+1}`,
  `event_uuid = derived_event_uuid(device_id, эпоха, device_seq)`, время сдвинуто на k · span (span копии 0 + 1 сутки).
  ЗАМЕР 2026-11-16: копии 2026 и 2027 — 2104 и 2105 субъектов, общих 42; с общей эпохой совпадают 45 126 событий,
  поэтому эпоха своя у каждой копии. Около 134 тыс. записей на копию.
- Запись — одно утверждение (claim) в порядке наблюдений и номеров утверждений. Ключ — 16 байт
  `uuid(memory_id(event_uuid, claim_index))`. Полезные данные — канонический UTF-8 JSON (sort_keys, без пробелов,
  ensure_ascii=False) полей наблюдения, источника и утверждения плюс `"v"` (номер версии).
- Наборы: N1 = 1 000 000 первых записей потока, N10 = 10 000 000 (N1 — его префикс). Записи, нужные динамике (§6),
  берутся из потока сразу после N1.
- Дубликаты ключей в потоке проверяются при генерации; хотя бы один — ошибка генерации, а не результат.

## 3. Общий слой данных

- Сегмент данных — до 1 000 000 записей подряд. Блок — около 64 КиБ в распакованном виде (по умолчанию горячих
  сегментов движка). Формат блока: `count u32 | keys 16·count | flags u8·count | ends u32·count | payloads`, сжатие
  zstd уровня 3 без словаря. Флаг 1 — надгробие (DELETE).
- Таблица блоков B: 8 байт на блок (смещение u40 | длина сжатого блока u24) — входит в адресные метаданные.
- А, SORT и SQLite используют ОДИН и тот же файл данных в порядке поступления. Б использует свой файл данных.
- Хеш ключа: `lo, hi` — 16 байт как два u64 little-endian; `h = splitmix64(lo ^ splitmix64(hi ^ seed))`; зерно
  хранится в заголовке адресного файла (А, SORT) или сегмента (Б). Вся арифметика по модулю 2^64.
- Проверка при открытии — CRC32 заголовка и границы массивов. BLAKE2b-256 всего файла пишется при запечатывании и
  проверяется отдельной командой `verify`; при открытии полная проверка не делается, иначе открытие было бы O(N).

## 4. Варианты и опорные решения

- **А (JLMADR01).** Каскад битовых карт с γ = 2.0: на уровне l ключ попадает в ячейку
  `((splitmix64(h + (l+1)·0x9E3779B97F4A7C15) >> 32) · m_l) >> 32`, `m_l = max(64, ⌈γ·n_l⌉)`; ключи, оставшиеся одни в
  ячейке, получают бит 1, остальные идут на следующий уровень; не более 64 уровней, неразмещённых после них нет
  (иначе — ошибка сборки). Опора ранга — u32 на каждые 512 бит. Номер слота — ранг бита. D[slot] = отпечаток f = 8 бит
  (младшие биты h) | номер блока r = ⌈log2(число блоков)⌉ бит, упакованы подряд. Поиск: P → D → сравнение отпечатка →
  чтение блока → поиск ключа в блоке. Ответ — только при полном совпадении ключа. На 10 млн — один адресный файл на
  все 10 сегментов данных (номер блока глобальный).
- **Б (JLMHPL01).** При запечатывании сегмента запись кладётся в корзину `h >> (64 − k)`, где 2^k — ближайшая к
  (распакованный объём сегмента / 64 КиБ) степень двойки; внутри корзины — порядок поступления; корзина = блок.
  Метаданные: таблица корзин (8 байт на корзину) + фильтр Блума сегмента 10 бит на ключ, 7 хешей двойным хешированием
  (`h1 = h`, `h2 = splitmix64(h ^ 0xD6E8FEB86659FD93) | 1`). Поиск: сегменты от нового к старому, фильтр → корзина →
  блок → ключ. Строки: Б10 (с фильтром, основная) и Б0 (без фильтра, только при одном сегменте).
- **SORT (простая опорная).** На адресный файл: отсортированный по `h >> 32` массив u32 и параллельный массив u32
  номеров блоков (8 байт на запись), mmap; поиск — двоичный поиск и чтение всех блоков-кандидатов с равным префиксом.
  Нужна, чтобы проверить, окупает ли P свою сложность против плоского массива.
- **SQLite (B-дерево).** `CREATE TABLE t(k BLOB PRIMARY KEY, blk INTEGER) WITHOUT ROWID`, page_size 4096, вставка в
  порядке поступления, затем VACUUM; поиск `SELECT blk` → тот же путь чтения блока. SQLite 3.39.4 из stdlib.
- PostgreSQL 18.7 и RocksDB — этап 3, не A2 (RocksDB владелец пока не разрешал ставить).

## 5. Проверки правильности (до любых замеров; провал = не вердикт, а исправление и повтор, раскрываемые в отчёте)

- **C1, исчерпывающая.** Для каждой записи каждой запечатанной структуры адрес(ключ) указывает на блок, где этот ключ
  лежит (А, SORT, Б, SQLite).
- **C2, сквозная.** 100 000 присутствующих ключей (равномерно, seed 11): возвращённые полезные данные побайтно равны
  сгенерированным.
- **C3, отсутствующие.** 100 000 случайных 16-байтных ключей (seed 12), которых нет в наборе по эталону
  (отсортированный массив ключей): ответ «нет».
- **C4, динамика.** После каждой фазы §6: все живые ключи (последняя версия побайтно), все удалённые (ответ «нет»),
  набор C3.
- **C5, мутанты** (на 100 000 записей): (а) испорчен номер блока в одном D; (б) ранг на 1 меньше; (в) сравнение
  отпечатка отключено и ключ в блоке не сверяется; (г) бит фильтра Блума у одного ключа сброшен. Каждого мутанта должна
  поймать хотя бы одна из C1–C3; не пойманный мутант — провал проверок.
- Ошибок должно быть 0 во всех проверках.

## 6. Динамика (база N1)

- Нагрузка — 500 000 операций в случайном порядке (seed 13): 250 000 INSERT (новые записи потока), 150 000 UPDATE
  (ключ равномерно из живых на этот момент, новые полезные данные из потока с `"v"` + 1), 100 000 DELETE (ключ
  равномерно из живых, надгробие).
- Хвост: операции пишутся в журнал хвоста (дозапись) и в словарь в RAM. Каждые T = 120 000 операций хвост
  запечатывается в новый сегмент данных (А: свой адресный файл; Б: свой размещённый сегмент с фильтром). Итого
  4 дельта-сегмента и 20 000 операций в хвосте.
- Поиск: хвост → дельта-сегменты от нового к старому → база; первое совпадение решает; надгробие — ответ «нет».
- Фазы с C4 и замерами: после каждого запечатывания; после рестарта (закрыть, открыть файлы, переиграть журнал хвоста);
  после слияния.
- Слияние А — только адресное: хвост запечатывается, затем один новый адресный файл над последней версией каждого
  живого ключа (номер блока — в любом сегменте); старые версии и удалённые ключи из адреса выпадают, данные не
  переписываются (доля мёртвых байт данных — в отчёт). Слияние Б — перезапись живых записей в новые размещённые
  сегменты (по 1 000 000): время и записанные байты.

## 7. Замеры

- **M1.** Адресные метаданные, байт на запись: весь адресный файл (заголовок, уровни, P, ранг, D, B, концовка) / число
  записей; для Б — таблицы корзин, фильтры, заголовки; для SQLite — размер файла БД. В динамике — на живой ключ.
- **M2, открытие.** Новый процесс; время от вызова open до ответа на первый запрос (присутствующий ключ, 21 разный
  ключ, медиана и максимум), файлы прочитаны заранее (тёплый кэш ОС). Число 4-КиБ страниц адресных структур, которых
  коснулся первый запрос (счётчик в обёртке доступа), и время того же первого запроса при чтении именно этих страниц
  без кэша ОС (CreateFileW c FILE_FLAG_NO_BUFFERING через ctypes).
- **M3, задержки** (описательно: прототип на Python). 100 000 запросов C2 в тёплом режиме и 10 000 с чтением блока
  без кэша ОС; раздельно t_addr (ключ → список блоков-кандидатов; для SQLite — SELECT) и t_payload (чтение блока,
  распаковка, поиск ключа); p50 / p95 / p99 в мкс. Плюс пакетная скорость вычисления адреса в numpy (ключей/с).
- **M4, сборка.** Время построения адресной структуры, записей/с (А, SORT, SQLite, Б с размещением).
- **M5, сжатие.** Сжатые байты данных на запись: порядок поступления и размещение Б; ρ = Б / поступление. Полный
  объём на запись = данные + M1, для А, SORT, SQLite, Б10.
- **M6, динамика.** По фазам: M1 на живой ключ; среднее и максимум просмотренных сегментов и прочитанных блоков на
  запрос (живые, удалённые, отсутствующие ключи); p50 / p95 / p99; время слияния; время рестарта с переигрыванием
  хвоста.

## 8. Правило решения

- **H-A ПРОХОДИТ**, если выполнены все:
  - A1: C1–C5 без ошибок для А на N1, N10, во всех фазах динамики и после рестарта.
  - A2: M1(А) ≤ 8,0 байта на N1 и на N10 и M1(А) ≤ 0,6 · M1(SORT) на обоих.
  - A3: медиана M2(А) на N10 ≤ 50 мс и ≤ max(2 · медиана N1, медиана N1 + 5 мс); среднее число страниц первого
    запроса (без блока данных) ≤ 16.
  - A4: среднее число прочитанных блоков на запрос живого ключа ≤ 1,05 до слияния и ≤ 1,01 после; на запрос
    отсутствующего ключа ≤ 0,05 до слияния; M1 на живой ключ после слияния ≤ 8,0.
- Не выполнено A2, A3 или A4 → **НЕ ПРОХОДИТ** с названием критерия. Провал A1 — ошибка реализации: исправить,
  повторить, раскрыть в отчёте; без нуля ошибок вердикта нет.
- **H-Б ПРОХОДИТ**, если C1–C5 без ошибок для Б (как A1), M1(Б10) ≤ 1,5 байта на N1 и N10 и полный объём Б10 меньше
  полного объёма А на N10. Класс цены сжатия по ρ на N10: ≤ 1,10 — дешёвая, (1,10; 1,25] — умеренная, > 1,25 —
  дорогая. Иначе — НЕ ПРОХОДИТ с названием критерия.
- Описательно, без влияния на вердикт: M3, M4, сравнение с SQLite и SORT по задержкам; сравнение открытия с нынешним
  стартом движка (ВЫВОД из E21: около 42 тыс. записей/с).

## 9. Прогноз (до кода)

- M1(А): N1 3,0–3,3 (точка 3,1), N10 3,3–3,7 (точка 3,5). M1(SORT) ≈ 8,0; отношение А/SORT ≈ 0,39 и 0,43.
  M1(SQLite) 26–31. M1(Б10) 1,25–1,30; Б0 0,02–0,04.
- Сжатые данные в порядке поступления — 35–55 байт на запись (неуверенно); ρ — 1,05–1,30 (точка 1,15). Тогда полный
  объём А меньше Б10: P(H-Б ПРОХОДИТ) ≈ 25%.
- M2(А) тёплое — 1–10 мс на обоих N; страниц первого запроса — около 6. Блоков на запрос живого ключа до слияния
  ≈ 1,01, отсутствующего ≈ 0,02, после слияния 1,00.
- M3 (Python): t_addr(А) p50 15–40 мкс, SQLite 4–10 мкс; t_payload (распаковка 64 КиБ) 50–150 мкс — основная доля.
- P(H-A ПРОХОДИТ) ≈ 75%; самые вероятные места провала — A3 (страницы при глубоких уровнях каскада) и A4.

## 10. Границы формулировок

- Прототип на Python/numpy: задержки — не оценка движка; честные p50/p95/p99 против SQLite и PostgreSQL — этап 3 с ядром
  на C++. Решение A2 опирается на правильность, байты, открытие и счётчики чтений, которые от языка не зависят.
- Корпус синтетический (E19/E20); числа сжатия относятся к нему.
- Одна машина, SSD C:, тёплый кэш ОС, кроме режима без кэша.
- «Без скрытого индекса» значит: нет структуры поиска, хранящей ключи. Адресный файл — статическая функция «ключ →
  блок», его байты учтены как индекс, а не скрыты. Хвост (≤ T записей в RAM) — тоже индекс, ограниченный T и не
  зависящий от N.
- Запросы «на момент времени», диапазоны и составные ключи — вне A2: возвращается последняя версия.
- В движок не встраивается.
