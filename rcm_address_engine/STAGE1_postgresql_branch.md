Числа из прежних отчётов:

- Старт движка 3,21 с на 134 тыс. записей (ЗАМЕР, E21, `design-docs/01-memory-engine.frame.md:132`). ВЫВОД: около
  42 тыс. записей/с, около 4 минут на 10 млн.
- Хранимый индекс 16 байт на объект снижал коэффициент с 11,5× до 3,5× (ЗАМЕР, E19b, `docs/memory_math.md:849,857`).

Главный вывод аудита. Движок индекс **не убрал и не сжал**: он его не хранит, а заново строит в RAM при каждом
старте. На диске 0 байт, но в памяти — обычные словари, и цена — полное декодирование данных при старте. Для СУБД
это непригодно. Переносим не код индекса, а принцип: адрес вычисляется из ключа порождающей функцией, хранится
только неустранимый остаток.

Что переиспользуем:

1. Принцип «операторы порождаются из зерна и хеша ключа, а не хранятся» (`pathstate.py`, `route.py`).
2. Блочную точность адреса с проверкой ключа в блоке (`Location`, `segments.py`).
3. Дисциплину проверки: контрольные суммы, дайджест файла, «совпадение отпечатка — только кандидат» (`paths.py`).
4. Битемпоральное разрешение (`truth.py`, `temporal.py`) — как эталон правильного ответа в тестах.

Что не переносится: `DerivedIndex` и `RouteTrie` (словари в RAM), LLM-генератор и энтропийные остатки (нет O(1)),
комплексные отпечатки путей (6 тыс./с), собственные WAL и сегменты (их роль выполняет PostgreSQL).

## 2. Как получить P и R по ключу без скрытого индекса

### 2.1. Граница (доказательство)

Если место записи не зависит от ключа (куча PostgreSQL, порядок поступления), то соответствий «ключ → место» n!,
и любое точное представление занимает не меньше log2(n!)/n ≈ log2(n) − 1,44 бита на запись: 18,5 бита при 1 млн,
21,8 бита при 10 млн. При адресе с точностью до страницы — около log2(число страниц) бит. Нулевого остатка здесь
не бывает: генератор не предскажет то, что от ключа не зависит. «Убрать индекс совсем» можно только если место
записи выбирает сам генератор (хеш-размещение), а в куче PostgreSQL место выбирает СУБД.

### 2.2. Схема

    h = hash64(ключ, зерно)                    G: порождается, не хранится
    slot = P(h)                                P: каскад битовых карт, 1–3 чтения памяти
    (отпечаток, страница) = D[slot]            R: поле фиксированной ширины, 1 чтение памяти
    строка = поиск ключа на странице кучи      1 чтение страницы, перепроверка ключа

- P — совершенная хеш-функция: на каждом уровне бит «ключ попал в ячейку один». Ключей в ней нет, дерева нет.
- R — номер страницы кучи, ⌈log2(число страниц)⌉ бит; отпечаток f бит отсекает чужие ключи.
- Точность 100%: ответ выдаётся только после сравнения с самим ключом в строке. Ложное совпадение отпечатка
  (доля 2^−f) стоит лишнего чтения страницы, но не неверного ответа.
- Массивы плоские, открываются через mmap; готовность не зависит от числа записей.

### 2.3. Оговорка о «скрытом индексе»

P и D по функции — индекс (статическая функция «ключ → страница»). Отличие от B-дерева: нет ключей, нет дерева,
размер в разы меньше.

| Структура, 1 млн записей | Байт на запись | Метка |
|---|---|---|
| SQLite B-tree, ключ 16 байт → адрес, после VACUUM | 28,1 | ЗАМЕР, `probes/sqlite_baseline.py` |
| То же, как построено | 30,9 | ЗАМЕР |
| SQLite, ключ int64 → адрес, после VACUUM | 21,2 | ЗАМЕР |
| Наша схема: P 3,1 бита + отпечаток 8 + страница 13 бит | 3,0 | P — ЗАМЕР (`probes/mphf_sizing.py`), сумма — ВЫВОД |
| Наша схема, 10 млн: 3,1 + 8 + 17 бит | 3,5 | ВЫВОД |
| PostgreSQL B-tree, ключ int8 / uuid | ≈ 22 / ≈ 31 | ВЫВОД из формата (кортеж 16 / 24 Б + указатель 4 Б, заполнение 90%); измерить |

P по замеру: 2,72 / 2,92 / 3,30 бита на ключ при γ = 1 / 1,5 / 2 (совпадает с γ·e^(1/γ)), опоры ранга 0,17–0,21
бита, среднее число проб 2,72 / 1,95 / 1,65; одинаково на 1 млн и 10 млн. Замер — только размеры на случайных
64-битных ключах, без записи на диск.

Схема известна (ИСТОЧНИК): SILT, Bitcask, BBHash, PTHash, RecSplit, ribbon- и xor-фильтры. В самом PostgreSQL уже
есть хеш-индекс (хранит хеш и адрес без ключа) и BRIN. Обученные индексы PGM и ALEX требуют сортировки.

## 3. Перенос в PostgreSQL

Соответствие (ИСТОЧНИК):

| Наше | PostgreSQL |
|---|---|
| Неупорядоченное хранилище | куча таблицы, страницы 8 КиБ |
| Физический адрес | `ctid` = (страница u32, позиция u16), 6 байт |
| R = номер страницы + перепроверка | «неточная страница» в bitmap-скане с recheck; чтение по `ctid` (Tid Scan, Tid Range Scan) |
| Подключение | расширение с собственным методом доступа индекса (`CREATE ACCESS METHOD`) |
| Базы сравнения | B-tree, хеш-индекс |

Сложности, которых нет в своём хранилище:

- UPDATE создаёт новую версию строки; HOT-обновление оставляет её на той же странице — адрес «страница» остаётся
  верным. Обычное обновление переносит строку на другую страницу — статическая функция устаревает.
- INSERT: статическая функция не дополняется. Нужен хвост (обычный B-tree на новые строки) и периодическая
  пересборка — как GIN с отложенным списком.
- VACUUM освобождает места, новые строки занимают старые адреса; перепроверка ключа защищает от неверного ответа.

### 3.1. Дескриптор (черновик адресного файла)

    заголовок 64 Б   магия | версия | записей u64 | страниц u32 | зерно u64 | γ | f бит | r бит | уровней | crc32
    уровни           до 40 × (смещение карты u64 | размер карты u32 | база ранга u32)
    P                битовые карты уровней подряд (u64) + опора ранга u32 на каждые 512 бит
    D                записей × (f + r) бит: отпечаток f | номер страницы r     ← дескриптор записи
    концовка         BLAKE2b-256

Дескриптор записи 21–25 бит плюс доля P 3,1 бита: 3,0–3,5 байта. Цель «≤ 8 байт» выполняется с запасом (ВЫВОД).

### 3.2. План этапа 2

Сначала дешёвая проверка без расширения на C:

1. Протокол с прогнозом и стоп-условиями, sha256, один круг Codex до фиксации.
2. Таблица в PostgreSQL на 1 млн и 10 млн строк. Адресный файл строится снаружи из `SELECT ctid, key`.
   Поиск: клиент вычисляет страницу, запрос идёт через Tid Range Scan с условием на ключ.
3. Сравнение с B-tree и хеш-индексом на той же таблице: байт на строку (`pg_relation_size`), время выполнения на
   сервере, число прочитанных страниц на запрос, время сборки, поведение после перезапуска с холодным кешем.
4. Динамика: вставки (хвост), HOT- и обычные обновления, удаления с VACUUM; доля устаревших адресов.
5. Только если проверка пройдена — настоящий метод доступа индекса на C (отдельное решение владельца).

Прогноз (до замеров):

- размер адресных метаданных в 6–9 раз меньше B-tree — вероятно;
- время точечного запроса при тёплом кеше — без кратного выигрыша (±20%): спуск по B-tree занимает малую долю
  времени запроса, остальное — разбор, планирование, исполнитель;
- выигрыш в разы возможен, когда индекс не помещается в RAM: 0 чтений диска на индекс против 1–3.

## 4. Риски

- Обновления и VACUUM в PostgreSQL делают статическую функцию устаревающей; цена хвоста и пересборок может съесть
  выигрыш на таблицах с частыми изменениями.
- Запросы по диапазону и сортировку схема не обслуживает — только точечный поиск.
- Метод доступа на C — большой объём работы (WAL, блокировки, VACUUM); браться только после проверки п. 2–4.
- Если поворот принят, утверждения «индекс = 0 байт на диске» (`docs/memory_math.md:857`, `design-docs/01`) нужно
  будет дополнить по итогам этапа 2.
