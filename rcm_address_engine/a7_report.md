## 0. Коротко

- **N1 (1 млн, 8 партиций), два прогона.** Ответ воспроизвёлся (ЗАМЕР):
  - B-tree на партиционированной таблице через родителя дороже, чем на одной таблице, в **1,251 / 1,228** раза;
  - прямой доступ в партицию — в **1,052 / 1,098** раза;
  - A6 целиком против одиночного B-tree — **×1,36 / ×1,33** по полной стоимости.

  У прямого клиента K_dir = 1,052 / 1,098. После арифметического вычитания измеренного g(k) — 1,003 / 1,049
  (чувствительность); механизмы остатка не разделены. Больше всего добавляет путь через родителя: около +35–50 мкс
  на каждый SELECT / UPDATE / DELETE (таймеры).
- **N10 (10 млн, 128 партиций), один прогон.** Знак обратный (ЗАМЕР): K_par = **0,807**, K_dir = 0,754,
  F_a7 / F_s = **0,853**. Одиночная таблица оказалась самой медленной.
  - Наблюдаемая разница сидит в одном месте основного потока: поиск **существующего** ключа в `s7` — 544–548 мкс
    против 223–256 у партиционированной таблицы. Поиск отсутствующего ключа и запись так не дорожают (таймеры B7).
  - Против прошлых прогонов (ИСТОЧНИК против ЗАМЕР) `s` медленнее контроля A5 на **+84%**, а `par` и `a7` — на +11%
    и +6% против A6.

  ВЫВОД: отношения измерены в совместном режиме трёх таблиц по 6,4 ГБ (граница §7). Почему в нём поиск
  существующих ключей у `s` существенно медленнее, не установлено. Кэш — правдоподобная гипотеза, но не замер
  (§3.3). Возможно, взаимодействие физического разбиения с памятью — часть эффекта партиционирования именно в этом
  режиме. Цена партиционирования для отдельно работающих систем на N10 не установлена.
- **Прогноз (§6 протокола):**
  - на N1 сбылся по всем K и F;
  - на N10 не сбылся по K_par, K_dir, K_route, F_a7/F_s и F_a7/F̂_par;

### 2.4. Диагностика N1 (ЗАМЕР, вне времени операций)

- **(д3) Парные чтения** на неизменяемом состоянии:
  - **медиана** разности `par` − `dir` на ключ положительна в 6 из 6 точек каждого прогона: 23,3–31,1 мкс;
  - **средняя** разность по точкам — r1: 24,2 / 29,8 / 28,3 / **−3,8** / 25,9 / 22,9; r2: 24,2 / 32,8 / 30,0 /
    10,1 / 29,0 / 28,3 мкс. В r1 cp3 знак меняется;
  - доля ключей, где `par` медленнее, 0,67–0,96.

  Это парное сравнение при данном порядке и данном состоянии подготовки запросов. Подготовленные запросы `dir` —
  отдельный текст на каждую партицию, а прогрев 200 ключей на 8 / 128 партиций (около 25 / 1,6 на партицию) может
  не пройти начальные частные планы каждого текста. Это гипотеза о хвосте и среднем `dir`, она не проверялась.
- **(д2) Через родителя при поиске:**
  - `force_generic_plan` p50 88–129 мкс, `force_custom_plan` 129–148 мкс;
  - общий план **быстрее** частного на N1 во всех точках.
- **(д4) EXPLAIN EXECUTE:**
  - у `par` в режиме auto план частный (по счётчикам), планирование 43–54 мкс, выполнение около 21 мкс;
  - у `s` и `dir` план общий, планирование 5–7 мкс;
  - «Subplans Removed» есть только у `par` при generic (поле есть, о полноте отсечения это не говорит).
- **(д5) Литеральный EXPLAIN:** планирование `s` 22 мкс, `par` 32–38, `dir` 22–30.
- **(д6) Блокировки поиска через родителя.** Первое и второе выполнение одного подготовленного запроса, каждое в
  своей транзакции:
  - generic: первое — 18 отношений (8 листьев, 8 их индексов, родитель и его индекс), второе — 10 (листья,
    родитель, один индекс);
  - custom: 4 и 4.

  Почему первое выполнение общего плана берёт больше (вероятно, построение плана), по коду не разделено. Это
  состав, не время.
- **(д1) Задержка поиска 2 000 живых ключей.** Значения зависят от того, какой маршрут первым читает общую выборку
  ключей точки C7. Выборка одна на точку (`Random(31 + cp)`), её 200 первых ключей — прогрев, на остальных 2 000
  проверка идёт без прогрева.
  - Пример: в r1 cp1 `par` первым — 573 мкс, затем `dir` на той же таблице — 102 мкс, `s` — 588.
  - ВЫВОД: (д1) сравнивает маршруты не чисто: первый маршрут по таблице `p7` прогревает страницы для второго.
    Сравнения `s` с `p7` без этой примеси в диагностике нет; его дают таймеры потока (§2.3).
- **Та же примесь в (д4)** (ЗАМЕР позиций в порядке диагностики). Ключи (д4) берутся из той же выборки:
  - `d4:s` медленный (387 / 711 мкс на N1, 950 / 204 / 364 на N10) ровно в тех точках (cp1, cp4, cp5), где он идёт
    **раньше** `d1:s`;
  - быстрый (19–21 мкс) — где он идёт после `d1:s` (cp0, cp2, cp3).

  ВЫВОД: (д4) у `s` измеряет первое или повторное чтение этих ключей, а не различие таблиц. Код сохраняет только
  сумму `Shared Hit` + `Shared Read` и исходные планы не сохраняет, поэтому разделить попадания и чтения задним
  числом нельзя.

## 6. Раскрытия и ограничения

- **Накладные расходы таймеров не одинаковы для маршрутов** (приложение §4): у `dir` два дополнительных вызова часов
  вокруг g(k). Величина не измерялась (ВЫВОД: доли микросекунды).
- **Партиции на 0,7–0,8% больше по страницам**, чем одиночная таблица при той же загрузке COPY (§1).
- **(д1) и (д4) смешаны с порядком чтения** общей выборки ключей (§2.4). Первый маршрут по `p7` прогревает страницы
  второму; `d4:s` медленный ровно там, где идёт раньше `d1:s`. Протокол этого не предусматривал.
- **Hit и read в EXPLAIN не разделены**: код суммирует `Shared Hit Blocks` и `Shared Read Blocks`, исходные планы
  не сохраняются.
- **(д3) может включать начальные частные планы** подготовленных запросов `dir` к листьям (гипотеза, §2.4).
- **Режим совместного прогона** (§7 протокола): на N10 он определил знак результата (§3.3).
- **Один прогон N10.**
- **Синтетический корпус, один клиент на Python, настройки PostgreSQL по умолчанию** (`shared_buffers` 128 МБ).
- **Время всех систем выше прошлых прогонов** (§3.3): таймеры, три таблицы и расписание — отличия методики.
- **Кэш ОС, память машины и файловый кэш Windows не измерялись**, поэтому механизм §3.3 не установлен.
- **llama-server на :8089 не трогался.** Его потребление памяти во время прогона не записывалось.

## 7. Исследовательский смысл (отдельно от чисел)

- Компактная вычисляемая адресация A6 требует таблицы, физически согласованной с секциями адреса.
- **На N1** цена этого требования измерена в одном прогоне и воспроизвелась:
  - прямой клиент платит ×1,05–1,10. После арифметического вычитания g(k) — ×1,00–1,05, механизмы остатка не
    разделены;
  - стандартный путь через родителя стоит около ×1,12–1,19;
  - A6 целиком дороже простого B-tree на одной таблице примерно на треть (×1,33–1,36) и на 10% дороже B-tree на той
    же партиционированной таблице (×1,10).
- **Прошлый разрыв A6/A5 на N1** численно близок к K_par, измеренному в одном прогоне (H / K_par ≈ 1,04–1,06).
  Причинного объяснения разрыва это не даёт.
- **На N10** при совместной работе трёх таблиц по 6,4 ГБ поиск существующих ключей у одиночного B-tree вдвое дороже.
  В таком режиме A6 и партиционированная таблица дешевле его (×0,85). Почему, не установлено: кэш — гипотеза.
  Возможно, это часть эффекта партиционирования в этом режиме.
- Насколько дорога партиция на N10 для отдельно работающей системы — открытый вопрос.
