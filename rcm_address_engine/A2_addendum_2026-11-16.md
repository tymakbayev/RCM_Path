# A2 — приложение 2026-11-16: итоги пилота P0 и изменения до основного прогона

Протокол: `A2_protocol.md`, редакция 2, sha256 `e68edb6c…0c36` (не меняется). Пилот P0 — 100 000 строк,
`results/a2_p0.json` и `results/a2_p0.log`. Это не вердикт. Все изменения ниже внесены ДО основного прогона,
как требует §7 (пилот P0).

## 1. Что подтвердил P0 (ЗАМЕР)

- Данные: payload 514–596 байт, медиана 522 (кириллица в UTF-8). 13,0 строки на страницу (7 688 страниц на
  100 000 строк). TOAST — 0 значений.
- Отклонение от прогноза §9: там было 19–23 строки на страницу. Следствия:
  - r = 17 бит на N1 и 20 бит на N10 (вместо 16 и 19);
  - таблица N10 ≈ 6,3 ГБ (вместо ≈ 4).
- Sidecar А: 3,07 байта на строку (r = 13 бит на 100 000), 12 уровней, исключений 0, C1 — 0 ошибок.
- Планы §4.5 совпали с протоколом:
  - статический поиск — Tid Range Scan, 1 буфер;
  - `UNION ALL … LIMIT 1` при попадании в дельту — Limit → Append, ветвь Tid Range Scan не выполнялась (loops = 0);
  - при промахе дельты выполняются обе ветви;
  - при несовпадении отпечатка — один Index Scan по дельте;
  - UPDATE и DELETE по ctid — Tid Scan;
  - ответы верны: v = 2 после UPDATE; удалённый ключ не найден.
- Методика `pg_statio` работает. На 2 000 запросов:
  - А — 1,0 обращения к куче и 0 к индексу на запрос;
  - B-tree — 1,0 к куче и 3,0005 к индексу.
  - EXPLAIN по верхнему узлу: А — 1,0, B-tree — 4,0.
- Бюджет: расчёт для N10 — меньше 6 часов, поэтому урезание по §7 не применяется. Оценка ×100 от пилота: загрузка
  ≤ 18 мин (завышена запуском генератора), загрузка Б ≈ 3 мин, сборка адреса ≈ 16 с, B-tree ≈ 15 с.

## 3. Изменение метода Б: исключения для «откатившихся» строк

**Факт (ЗАМЕР).** При загрузке `INSERT … SELECT … ORDER BY` в новую пустую таблицу 391 строка из 100 000 (0,39%)
нарушила инвариант §4.3. Объяснение (ВЫВОД, по устройству кучи PostgreSQL): когда строка не помещается на текущую
страницу, сервер записывает её остаток свободного места в карту FSM и может взять более раннюю страницу, где
осталось место для более короткой строки. Порядок вставки не гарантирует монотонности страниц. По правилу §4.3 это
нарушение было бы результатом «схема границ непригодна». Найдено до прогона — поэтому метод меняется здесь:

- После загрузки строки Б перебираются в порядке загрузки (корзина, seq). Строка «откатилась», если её страница
  меньше максимума страниц всех строк, загруженных до неё.
- Откатившиеся строки идут в список исключений Б: 16 байт ключа и u32 страницы, по возрастанию ключа.
- start_j считается только по строкам, которые не откатились. Корзина, у которой все строки откатились, считается
  пустой и получает start следующей непустой.
- Формат JLMHPL01: в заголовок добавлено число исключений; список лежит после массива начал. Байты списка входят в
  M1 Б.
- Поиск Б: сначала исключения (двоичный поиск); при попадании — одна страница. Иначе — диапазон корзины.
- Инвариант §4.3 теперь звучит так: каждая строка либо в исключениях с верной страницей, либо в диапазоне своей
  корзины. Проверяется исчерпывающе (C1). Число откатившихся строк — отдельный результат в отчёте.
- Новый мутант C5 (е): исключения Б не просматриваются. Должен быть пойман C2, когда исключения есть.
- Критерии H-Б (§8) не меняются: метаданные ≤ 1,0 байта на запись (вместе с исключениями), ≤ 2,5 обращения к куче.
  Расчёт: 0,4% × 20 байт ≈ 0,08 байта на запись.

## 4. Пиковый диск (уточнение §7)

На N10: таблицы А и Б по ≈ 6,3 ГБ, сортировка при загрузке Б ≈ 6 ГБ, временная таблица порядка ≈ 0,4 ГБ, WAL ≤ 1 ГБ.
Итого около 20 ГБ. Таблицы N1 удаляются до N10.
