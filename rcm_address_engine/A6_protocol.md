## 1. Вопрос

Исследовательская гипотеза RCM Path (отчёт начинается с неё, отдельно от критериев): можно ли держать изменяющиеся
данные под компактной вычисляемой адресацией так, чтобы на проверенных размерах с N не росли ни стоимость
обслуживания адреса на операцию, ни самая длинная пауза обслуживания адреса, и при этом **раунд большого слияния не
создавал отображения «ключ → страница» для всей таблицы**, а его временные пары были ограничены одной партицией?
Поиск остаётся «адрес → одна страница кучи», адресные данные — компактными.

Что разрешено и не считается нарушением (R4): опубликованная структура адреса; журнал хвоста; журналы прогонов
(пары дельты — это и есть адресуемая дельта A4); частичный выход активного слияния ярусов; эталон проверки в
процессе испытательного стенда (обслуживающему коду он недоступен: `a6_lsm.py` получает только результат чтения
партиции).

Чем A6 отличается от A5 по существу: физическая организация таблицы согласована с секциями адреса. Это стандартное
средство PostgreSQL (декларативное партиционирование `PARTITION BY HASH`), а не своё хранилище.

H-A6 — измеримая форма (§6) на 1 и 10 млн строк. Асимптотика и гарантированный предел задержки не проверяются: это
один прогон на размер.

## 2. Конструкция

### 2.1. Что наследуется из A5 без изменений

- Журнал хвоста JLMDLOG1, пакеты по 1 000 операций, единственный писатель, `RETURNING ctid`, запечатывание каждые
  T_run = 30 000 зафиксированных операций.
- Прогоны: журнал (ключ 16 + страница 4), сортировка по (h, k), h = `key_hash(k, SEED_SECT)`, секции прогона —
  старшие биты h. Дубли — по полному ключу.
  - **Число секций (R3):** S(n) = 1 при n ≤ σ, иначе 2^ceil(log2(n / σ)) — всегда целое ≥ 1. Запечатанный прогон из
    30 000 ключей → 1 секция.
  - **Пустой прогон** (хвост без живых записей): одна секция без файла JLMADR01, журнал нулевой длины. Поиск по нему
    кандидатов не даёт. Как в коде A5.
- Приоритеты прогонов, инвариант хронологии ярусов, слияния ярусов шагами по секциям выхода, одно активное слияние,
  закрепление входов, не больше одного шага слияния на границу пакета (A5 §2.2).
- Начало раунда большого слияния (A5 §2.3):
  - по монотонному счётчику f · N₀ (f = 0,1), на первой границе без активного слияния ярусов;
  - принудительное запечатывание хвоста; W = номер последней зафиксированной операции;
  - все существующие прогоны получают класс «до W» и больше не сливаются.
  - Конец раунда: прогоны «до W» удаляются после последней секции, счётчик отсчитывается от W, N₀ пересчитывается.
- Поиск `UNION ALL … LIMIT 1` по страницам-кандидатам от нового уровня к старому, проверка `k = $1` и MVCC.
- Контракт A4: читатели сериализованы с пакетами писателя, обслуживание — между пакетами при остановленных клиентах.
  Поэтому **во время шага раунда таблица не меняется** (R1).
- **Контракт писателя (R2):** `k NOT NULL`, ключ уникален среди живых строк и никогда не меняется (UPDATE не трогает
  `k`).
- **Предпосылка:** нет незажурналированных перемещений строк (`VACUUM FULL`, `CLUSTER`, переписывание таблицы или
  партиции, `ATTACH/DETACH PARTITION`, сторонние писатели). Обычный `VACUUM` разрешён.
- Ядро адреса `a2_core.py`, код A4 и A5 не меняются. Новое — `a6_pghash.py`, `a6_lsm.py` (на основе `a5_lsm.py`) и
  `a6_run.py`.

### 2.2. Таблица

- `CREATE TABLE a6_{n} (seq bigint NOT NULL, k uuid NOT NULL, v int NOT NULL, payload text NOT NULL) PARTITION BY
  HASH (k)` и S_base партиций `a6_{n}_p{j} … FOR VALUES WITH (MODULUS S_base, REMAINDER j)`,
  `autovacuum_enabled = false` у каждой. Все партиции с одним модулем, полный набор остатков 0 … S_base − 1.
- S_base = S(N₀) при σ = 2¹⁷ — как в A5: N1 → 8 партиций (в среднем 125 000 строк), N10 → 128 (около 78 000).
  Число партиций фиксировано на весь прогон данного N.
- Индекса по `k` нет.

### 2.3. Функция партиции в клиенте

- Клиент вычисляет партицию ключа сам: g(k) = `hash_combine64(0, uuid_hash_extended(k, HASH_PARTITION_SEED))
  mod S_base`. Это схема PostgreSQL для одной ненулевой колонки uuid при одинаковом модуле всех партиций (ИСТОЧНИК:
  исходники PostgreSQL — `partbounds.c: compute_partition_hash_value`, `get_partition_for_tuple`;
  `uuid.c: uuid_hash_extended`; `hashfn.c: hash_bytes_extended`; `HASH_PARTITION_SEED = 0x7A5B22367996DCFD`). При
  одном модуле наибольший модуль равен S_base, и остаток прямо даёт номер партиции (R2).
- Реализация — `a6_pghash.py`, скалярная и numpy: беззнаковая 32- и 64-битная арифметика с переполнением, ровно
  16 байт UUID в сетевом порядке (`uuid.UUID.bytes`, не `bytes_le`), слова хеша читаются в порядке little-endian (как
  на сервере x86-64). Сервер зафиксирован: PostgreSQL 18.7; после обновления сервера проверка повторяется (R2).
- **Факт до фиксации протокола** (проверка инфраструктуры, не замер гипотезы; ЗАМЕР): 20 000 случайных ключей —
  `uuid_hash_extended` сервера совпал со скалярной реализацией у всех; numpy совпал со скалярной у всех;
  маршрутизация строк сервером по партициям совпала с g(k) у всех при S = 8 и S = 128; прямая вставка в чужую
  партицию отклонена (`CheckViolation`).
- **Проверка до прогона (R2):** для всех N строк после загрузки и для всех ключей вставок потока g(k) — скалярной и
  numpy — сравнивается с **остатком партиции**, в которой лежит строка (`tableoid` → имя партиции → её остаток из
  `pg_get_expr(relpartbound)`). Для ключей вставок, которых ещё нет в таблице, — со `satisfies_hash_partition`.
  Требуется 100% совпадение, иначе исход НЕ УСТАНОВЛЕНО до исправления.
- **Проверка во время прогона:** все записи A6 идут прямо в партицию g(k). PostgreSQL проверяет ограничение
  партиции при прямой вставке в неё; отказ считается ошибкой применения. Сценарии §4 подтверждают, что вставка в
  чужую партицию и UPDATE ключа в листовой партиции с выходом за её ограничение отклоняются.
- Это сильная проверка для данных опыта, но не доказательство правильности функции на всех UUID (R2).

### 2.4. Адрес

- **База** — S_base файлов JLMADR01, по одному на партицию: секция базы j = партиция j, номера страниц — страницы
  кучи этой партиции. Секция базы ключа — g(k), а не старшие биты h. Это единственное изменение функции секций
  относительно A5.
- **Хвост и прогоны** — как в A5. Страница в записи относится к партиции g(k): ключ однозначно задаёт партицию,
  поэтому номер страницы без номера партиции однозначен.
- **Поиск:** j = g(k), кандидаты по всем уровням, запрос
  `(SELECT … FROM a6_{n}_p{j} WHERE ctid >= '(p,0)' AND ctid < '(p+1,0)' AND k = $1) UNION ALL … LIMIT 1` —
  все кандидаты в одной партиции.
- **Запись:** `INSERT INTO a6_{n}_p{j} … RETURNING ctid`; `UPDATE a6_{n}_p{j} … WHERE ctid = … AND k = … RETURNING
  ctid`; `DELETE FROM a6_{n}_p{j} WHERE ctid = … AND k = …`.

### 2.5. Раунд по партициям (заменяет шаги прохода и построения A5)

- **Шаг раунда s** (s = 0 … S_base − 1 по порядку, один шаг на границу пакета):
  - `COPY (SELECT k, (ctid::text::point)[0]::int4 FROM a6_{n}_p{s}) TO STDOUT (FORMAT binary)` в своей транзакции —
    вся партиция целиком, без границы по страницам;
  - построение JLMADR01 секции s нового поколения из прочитанного;
  - публикация в манифесте (переключается только секция s) вместе с номером следующего шага s + 1; затем удаление
    старого файла секции s.
- Прочитанные пары партиции живут только в памяти и только внутри шага. Единственный файл, который создаёт шаг, —
  новый файл секции s; единственный удаляемый — её старый файл. **Рабочих файлов нет.**
- **Состояние раунда в манифесте (R1)** — публикуется на каждой границе, где оно меняется:
  - W и счётчик операций на W;
  - номер следующего неопубликованного шага;
  - поколение и число ключей каждой опубликованной секции базы, поколение нового раунда;
  - для каждого прогона — номер, приоритет, ярус, число секций, смещения, **класс «до W»**;
  - счётчики (номер операции, номер пакета, монотонный счётчик, N₀, следующие номера прогонов и приоритетов), номер
    журнала хвоста и число его зафиксированных операций на момент публикации;
  - номер активного слияния ярусов.
- **Рестарт посреди раунда — раунд продолжается** со следующего неопубликованного шага с прежним W:
  - всё перечисленное восстанавливается из манифеста, хвост — из журнала (метки C, как в A4);
  - частичный выход активного слияния ярусов отбрасывается, его входы остаются опубликованными и закреплёнными
    больше не являются; поиск снова идёт по всем входам (как в A5);
  - рабочих файлов нет, терять нечего.
  - Продолжение безопасно только с согласованной границы публикации. Аварийное завершение внутри публикации — вне
    контракта A4.

### 2.6. Почему раунд правильный

Инвариант A4: для каждого живого ключа хотя бы один опубликованный уровень указывает на страницу его видимой версии.

- **Ключ менялся после W.** Самая новая запись «после W» — в хвосте или в прогоне «после W». Раунд эти уровни не
  удаляет, слияния ярусов «после W» сохраняют самую новую запись по приоритету.
- **Ключ не менялся после W.** Строка лежит в партиции g(k) на постоянной странице p: обычный `VACUUM` живую версию
  не переносит (предпосылка). Шаг s = g(k) читает всю партицию после W, таблица во время шага не меняется, поэтому
  шаг видит (k, p). Новая секция s указывает на p.
- **Строки, записанные после W** (в том числе на новых страницах партиции), либо попали в чтение шага, либо записаны
  после него. В обоих случаях их покрывают уровни «после W»; лишняя запись в базе на правильную на момент чтения
  страницу правильности не вредит.
- **Удалённый ключ** отсекается проверкой `k = $1` и MVCC. **Пустая партиция** даёт пустую секцию.
- **До публикации секции s** верна старая секция s вместе с прогонами «до W» — состояние A4. Прогоны «до W» общие для
  всех секций, поэтому удаляются только после последней.
- **Рестарт с продолжением:** W, классы прогонов, приоритеты и опубликованные секции восстанавливаются из манифеста,
  хвост — из журнала. После рестарта состояние то же, что до него; оставшиеся шаги читают партиции после W.

## 3. Данные, поток, контроль

- **Данные и поток** — как в A4/A5: N1 (sha256 потока `1f685ebe…47d5`) и N10 (`1bdeb7fb…313a`); 500 000 операций;
  seed 13. Совпадение потока записывается прогоном.
- **Загрузка A6:** `COPY` из генератора в родительскую таблицу (PostgreSQL распределяет строки по партициям), затем
  `VACUUM (ANALYZE)`, затем проверка §2.3.
- **Контроль — та же партиционированная таблица с B-tree**, то есть стандартное решение PostgreSQL для такой
  таблицы (R7):
  - `c6_{n}` с тем же `PARTITION BY HASH (k)` и тем же S_base;
  - заполнение на сервере сразу после загрузки A6, **по партициям в явном порядке**:
    `INSERT INTO c6_{n}_p{j} SELECT * FROM a6_{n}_p{j} ORDER BY ctid` для каждого j. Причина серверного заполнения:
    загрузка контрольной таблицы N10 из клиента шла около 80 минут в A4 и A5 (не замер);
  - **проверка раскладки:** для всех строк страница ключа в c6 и в a6 сравнивается (обе таблицы читаются по
    партициям, пары сравниваются по ключу). Сообщается доля совпадений. Если она не 100%, утверждение ослабляется до
    «одинаковые данные, сопоставимые размеры» и указываются различия в числе страниц;
  - `CREATE UNIQUE INDEX c6_{n}_bt ON c6_{n} USING btree (k)` — локальный B-tree в каждой партиции;
    `VACUUM (ANALYZE)`;
  - **основной контроль** ищет и пишет **через родительскую таблицу по ключу** (`WHERE k = $1`), отсечение
    партиций делает PostgreSQL. Это обычное использование партиционированной таблицы. Часть разницы с A6 поэтому
    дадут маршрутизация и планирование, которые A6 обходит;
  - **диагностический вариант контроля** (R7) — только в точках C4, на той же выборке запросов: поиск прямо в
    партиции g(k) по её локальному B-tree, стоимость g(k) включена. Сообщаются обращения и задержка в клиенте.
    Полного прогона операций у этого варианта нет, поэтому о его полной стоимости выводов нет.
- **Сравнение с A5** (одна таблица, B-tree на одной таблице) — по числам отчёта A5 (ИСТОЧНИК). Время между прогонами
  плавает примерно на ±15% (раскрытие A5), это указывается.
- **VACUUM** у обеих систем — после операций 240 000 и 480 000 (по родительской таблице, то есть всех партиций).
- **Раунды** — как в A5:
  - N1 — естественные (около каждых 100 000 операций);
  - N10 — порог 1 000 000 в потоке не достигается; один раунд запускается принудительно на операции 150 000 и идёт
    шагами между реальными пакетами (128 шагов, около 128 000 операций). B на N10 поэтому — условная оценка: таблица
    на раннем и на естественном пороге различается не только размером дельты, но и числом живых строк, мёртвых
    версий и страниц (R6). S4 на N10 дополнительно проверяется воспроизведением естественного цикла (§5);
  - финальный раунд на обоих размерах — в конце, шаги подряд без операций, затем последняя точка C4. Его
    непрерывная длительность — отдельной строкой, в S4 не входит. В нём же — замер памяти шага (§5).
- **Рестарт PostgreSQL и клиента** — в конце потока, как в A5. Плюс на N1 один рестарт клиента **посреди рабочего
  раунда** (после половины шагов): адрес закрывается и открывается из манифеста, раунд продолжается на реальной
  таблице. Время этого рестарта — в общей остановке клиентов, не в S4.
- **Контрольные точки C4** — 13 на размер, как в A4/A5. Плюс по одной точке посреди каждого рабочего раунда, после
  половины шагов, и одна сразу после продолжения раунда на N1.
- **Байты адресных данных** — на каждой границе пакета.
- **Свидетели** — 200 ключей после каждого запечатывания, шага слияния и шага раунда: затронутые ключи шага; у шага
  раунда — ключи его партиции, в том числе изменённые после W, и ключи на первой и последней странице партиции.

## 4. Правильность

- **C4, применение операций, свидетели** — 0 ошибок. Проверка функции партиции до прогона — 100%. Отказов ограничения
  партиции во время прогона — 0.
- **Сценарии** (таблица 10 000 строк, T_run = 50, σ = 256; S_base = 8 задаётся **принудительно**, по формуле было бы
  64 — R3). Сценарии A4 и A5, не связанные со срезами страниц, плюс:
  - ключ, обновлённый до W и после W, с переносом страницы внутри уже перестроенной партиции;
  - ключ, перенесённый во время раунда внутри ещё не перестроенной партиции, затем её шаг;
  - INSERT во время раунда в уже перестроенную партицию, затем UPDATE с переносом;
  - DELETE во время раунда в перестроенной и в неперестроенной партиции;
  - `VACUUM` с повторным использованием места посреди раунда;
  - пустая партиция (все её строки удалены): шаг строит пустую секцию, затем INSERT в неё;
  - ключи на первой и последней странице партиции;
  - **одинаковый номер страницы в разных партициях** у разных ключей (R8);
  - рестарт посреди раунда одновременно с активным слиянием ярусов, продолжение и завершение раунда;
  - сценарии A5 **R2** (хронология слияний) и **R4** (искусственная коллизия h);
  - ключи из всех S_base партиций;
  - **отрицательные:** прямая вставка строки в чужую партицию и UPDATE ключа в листовой партиции на значение другой
    партиции отклоняются PostgreSQL (R2).
- **Мутанты и их детерминированные свидетели** (R8). Каждый должен быть пойман:
  - (а)–(г) из A4 — со свидетелями A4;
  - из A5, со свидетелями A5: (ж) прогон «до W» сливается с прогоном «после W»; (з) поиск во время слияния ярусов
    берёт неготовую секцию выхода; (и) W без принудительного запечатывания; (к′) приоритет выхода −max входов;
    (л) слияние сравнивает только h;
  - (д) прогоны «до W» удаляются после публикации первой секции, а не последней. Свидетель: ключ перенесён до W в
    ещё не перестроенной партиции (старая база указывает на прежнюю страницу, правильная запись только в прогоне
    «до W»); поиск сразу после первой публикации;
  - (е′) последняя партиция не перестраивается: раунд заканчивается после S_base − 1 шагов. Свидетель: такой же ключ
    в последней партиции; поиск после конца раунда;
  - (м) шаг читает партицию s, а публикует результат как секцию (s + 1) mod S_base. Свидетель: после переключения
    проверяются **все** живые ключи обеих затронутых партиций (не выборка: случайный кандидат может совпасть с
    правильной страницей);
  - (н) клиент вычисляет партицию по старшим битам h вместо функции PostgreSQL. Свидетель: проверка функции до
    нагрузки (§2.3) и ключ, для которого две функции заведомо расходятся;
  - (о) после рестарта посреди раунда W заменяется текущим номером операции, прогоны, запечатанные после старого W,
    становятся «до W» и удаляются в конце раунда. Свидетель: ключ в уже перестроенной партиции перенесён после её
    чтения; его запись запечатана между старым W и рестартом; после рестарта ключ не меняется; поиск после конца
    раунда;
  - (п) поиск для кандидатов из прогонов обращается к партиции (g(k) + 1) mod S_base. Свидетель: сценарий
    одинакового номера страницы в разных партициях и ключ, найденный только через прогон;
  - (р) после рестарта раунд продолжается, пропуская следующий неопубликованный шаг. Свидетель: ключ, перенесённый
    до W в пропущенной партиции; поиск после конца раунда.
  - (к) из A5 эквивалентен (приложение A5 §1): запускается и сообщается, в S0 не входит.
- Самопроверка ядра (`a2_selftest_core.py`) и проверка без SQL (как `a5_selftest_lsm.py`, с партициями в памяти и
  рестартом с продолжением раунда) — повторно.

## 5. Замеры

Всё из A5 §5, кроме рабочих файлов. Обращения считаются по сумме партиций (`pg_statio` по всем партициям таблицы).

- **Пауза границы пакета** — всё обслуживание адреса на одной границе (определение A5 R7): запечатывание, шаг
  слияния, шаг раунда (чтение партиции, построение, сброс и fsync, публикация, закрытие и открытие mmap, удаление
  файла), конец раунда. Максимум, p99, распределение; время пакета вместе с обслуживанием (p50, p95, p99, max).
  Общая максимальная остановка клиентов (VACUUM, рестарт) — отдельно, в S4 не входит.
- **Шаг раунда (R5):** строки и страницы партиции; время чтения и построения по отдельности (максимум и
  распределение); расстояние в пакетах от последнего VACUUM; число строк партиции, записанных (I/U) с её
  предыдущего чтения или с загрузки.
- **S5, файлы (R4):** обслуживающий код создаёт и удаляет файлы только через учётные функции; для каждого шага
  раунда записываются все созданные и удалённые пути. Плюс проверка каталога адресного слоя на каждой границе: нет
  файлов, кроме опубликованной структуры, журнала хвоста, манифеста и частичного выхода активного слияния.
- **S5, память шага (R4):**
  - логический размер пар шага — строки партиции × 20 байт, максимум по шагам (все рабочие раунды);
  - **фактический пик памяти шага** — `tracemalloc` (учитывает буферы COPY, массивы numpy, сортировку и
    построитель), измеряется только в финальном раунде, чтобы накладные `tracemalloc` не попали в паузы рабочих
    раундов. Сообщается пик сверх памяти до шага.
- **Партиции:** строки и страницы каждой партиции в начале и в конце (минимум, максимум, коэффициент вариации);
  размер таблицы против таблицы A5 на том же N (ИСТОЧНИК) — цена партиционирования.
- **Функция партиции:** результат проверки до прогона; время вычисления на ключ в клиенте.
- **Контроль:** обращения при выполнении (верхний узел) и обращения планирования (`EXPLAIN … BUFFERS`) отдельно;
  задержка в клиенте; фактическая высота B-tree партиций (по структуре индекса); то же — у диагностического варианта.
- **Открытие** в новом процессе, 21 раз.
- **Пиковый RSS** клиента — как в A5 (`GetProcessMemoryInfo`), с той же оговоркой про эталон проверки в процессе.
- **Воспроизведение естественного цикла без SQL (R6)** — N1 и N10, тот же планировщик A6:
  - начальное состояние: база из всех ключей N (страницы случайные, партиции по g(k)), пустая дельта;
  - поток операций того же состава, что в прогонах; чтение партиции заменено чтением её ключей из памяти;
  - прогрев: до начала первого раунда W₁; **измеряемый цикл — от W₁ до W₂** (начало следующего раунда), в нём ровно
    один полный раунд — начатый на W₁; остановка на W₂;
  - M = W₂ − W₁ (операций). Сообщаются M и задержка запуска раунда из-за активного слияния ярусов.
  - Результаты: максимум суммарной работы границы без PostgreSQL; отдельно — границы с совпадением работ.
- **Установившееся обслуживание на операцию (R6):** `(запечатывания + шаги слияния + начало и конец раунда в цикле
  W₁…W₂ воспроизведения) / M + B / M`, каждый компонент один раз; время имитированных шагов раунда в первое слагаемое
  не входит.
  - B — измеренная сумма шагов раунда в PostgreSQL на этом N: среднее по рабочим раундам и разброс; финальный раунд
    отдельной строкой. На N10 B из принудительного раунда — условная оценка.
- **Оценка совпадения работ на N10 (R5, описательно):** для каждой границы воспроизведения с шагом раунда время
  имитированного шага заменяется измеренным максимумом шага раунда в PostgreSQL на N10 (чтение и построение, без
  двойного учёта построения), остальные работы границы берутся из воспроизведения. Сообщается максимум. Это оценка,
  а не замер, и в правило решения не входит.

## 6. Правило решения

Три исхода: ПРОХОДИТ, НЕ ПРОХОДИТ (критерий), НЕ УСТАНОВЛЕНО (ошибка реализации или незавершённый прогон).

- **H-A6 ПРОХОДИТ**, если выполнены все условия:
  - **S0, правильность:** 0 ошибок C4 во всех точках N1 и N10; 0 ошибок применения и 0 отказов ограничения
    партиции; проверка функции партиции 100%; все сценарии верны; все свидетели верны; мутанты §4 пойманы.
  - **S1, обслуживание:** установившаяся стоимость на операцию на N10 ≤ 1,5 × той же на N1 — по времени и по
    логическому объёму. На N10 — условная оценка.
  - **S2, поиск:** среднее обращений на запрос живого ключа ≤ того же у основного контроля в каждой точке на N1 и
    N10.
  - **S3, байты:** опубликованная основная структура (включая закреплённые входы и готовые секции выхода активного
    слияния) ≤ 8,0 байта на живой ключ в каждой точке C4 и на каждой границе пакета.
  - **S4, паузы обслуживания адреса** — те же пороги, что в A5, ради сравнимости (владелец 2026-11-16: порог 1 с —
    наше ожидание, а не аксиома; он сохраняется, чтобы A5 и A6 мерились одной меркой):
    - максимальная пауза границы пакета в рабочем режиме ≤ 1,0 с на N1 и на N10;
    - максимальная пауза на N10 ≤ 1,5 × максимальной на N1;
    - в воспроизведении естественного цикла N10 максимальная суммарная работа границы ≤ 1,0 с.
    - **Граница вывода (R5):** S4 проверяет реальный (на N10 — принудительный) раунд в PostgreSQL и отдельно
      воспроизведение без SQL. Естественный SQL-цикл на N10 не установлен; оценка совпадения работ (§5) стоит рядом.
  - **S5, раунд без отображения для всей таблицы (новое):**
    - ни один шаг раунда не создаёт файлов, кроме новой секции своей партиции, и на каждой границе в каталоге нет
      посторонних файлов (§5);
    - логический размер пар шага на N10 ≤ 1,5 × того же на N1;
    - фактический пик памяти шага (финальный раунд) на N10 ≤ 1,5 × того же на N1.
- **Формулировка вердикта** — «критерии адресного слоя». Рядом стоят общая эффективность (полная стоимость на
  операцию против основного контроля, общая максимальная остановка клиентов), диагностический контроль и сравнение
  с A5 (ИСТОЧНИК).

## 7. Прогноз (до кода)

Вероятности ниже — субъективные предварительные оценки (R9).

- **Обращения:** A6 1,00–1,05. Основной контроль 3,0–4,0: в партиции 78–140 тыс. строк, высота B-tree 2–3 уровня
  плюс страница кучи; точную высоту даст структура индекса. Диагностический контроль — столько же обращений при
  выполнении, меньше обращений планирования.
- **Пауза границы пакета** — максимум суммы совпавших на границе работ (R9):
  - N1: шаг = чтение партиции (около 10,5 тыс. страниц, 0,25–0,7 с по шагам прохода A5) + построение (около 0,08 с)
    + публикация и fsync; на той же границе может быть запечатывание (до 0,04 с) → максимум 0,5–0,9 с. В A5 самые
    длинные срезы — последний срез с недавно записанными страницами (0,73 и 1,13 с) и срезы после VACUUM. Здесь
    записи распределены по всем партициям хешем, поэтому горячие страницы делятся между шагами примерно поровну;
    общих причин задержек PostgreSQL (контрольные точки, VACUUM) это не убирает. P(S4 на N1) ≈ 60%;
  - N10: 0,15–0,4 + 0,07 → максимум 0,25–0,5 с; отношение N10/N1 0,3–1,0.
- **Установившееся обслуживание:** B N1 около 3,0–4,8 с → 31–50 мкс на операцию; B N10 около 25–32 с → 28–35;
  отношение 0,6–1,1.
- **Байты:** как в A5 — пик N1 5,5–6,0, N10 4,6–4,8.
- **S5:** посторонних файлов 0; логический размер пар шага N1 около 2,6–2,9 МБ (до 141 тыс. строк), N10 около
  1,6–1,7 МБ; фактический пик памяти шага в 2–4 раза больше логического.
- **Таблица:** партиционирование добавляет ≤ 1% страниц. Раскладка c6 совпадает с a6 на 100%.
- **Основной контроль:** запись и поиск через родителя дороже, чем на одной таблице: время операций контроля на
  5–25% больше, чем у контроля A5.
- **Полная стоимость A6 против основного контроля:** N1 ×1,1–1,4, N10 ×0,9–1,1.
- **P(H-A6 ПРОХОДИТ) ≈ 50%.** Риски: функция партиции на ключах вставок, S4 на N1, накладные Python на множество
  подготовленных запросов (свой набор на партицию).

## 8. Границы

- Контракт A4 и предпосылка §2.1. Шаги — модель инкрементальной работы, не фоновый процесс.
- **Изменена физическая организация таблицы.** Результат относится к хеш-партиционированной таблице. Число партиций
  фиксировано на прогон; при росте N в разы нужна переразбивка таблицы — это переписывание, вне A6. На 100 млн при
  σ = 2¹⁷ это около 1 024 партиций (ВЫВОД); поведение PostgreSQL при таком числе партиций (планирование у
  контроля, каталог, открытые файлы) здесь не проверяется.
- **Клиент повторяет хеш-функцию PostgreSQL** — внутреннюю функцию сервера. Сервер зафиксирован (18.7); после
  обновления проверка §2.3 повторяется. Проверка охватывает ключи опыта, а не все UUID.
- **Временные пары одной партиции в памяти шага** существуют только внутри шага. Это тот же вид данных, что держало
  построение базы A2/A4 (там — на всю таблицу). Отчёт сообщает их логический и фактический размер; считать ли это
  допустимым — решает владелец.
- S1 и S4 — ограниченные отношения на двух размерах в одном прогоне, не асимптотика. S4 ограничивает паузы
  обслуживания адреса, а не все остановки клиентов; естественный SQL-цикл на N10 не установлен.
- Python-клиент, тёплый кэш ОС, одна машина, настройки PostgreSQL по умолчанию, синтетический корпус. Только
  точечный поиск.
- Новизна приёма не утверждается: партиционирование таблицы и уплотнение по партициям — известные приёмы.

## 9. Рассмотренные альтернативы (не выбраны)

1. **Партиционирование `LIST` по колонке секции, которую вычисляет клиент своим хешем.** Не нужно повторять хеш
   PostgreSQL, но появляется колонка, которую база не может проверить на согласованность с ключом. Не выбрано:
   `HASH (k)` проверяет сам PostgreSQL.
2. **Независимая дельта в каждой партиции** (свои хвост, прогоны и раунд). Раунд одной партиции не зависел бы от
   других, но число файлов и запечатываний растёт в S_base раз. Не выбрано: A6 меняет только то, что нужно, чтобы
   убрать рабочий файл, и остаётся сравнимым с A5.
3. **Отдельные шаги чтения и построения** (как в A5) с хранением прочитанных пар одной партиции между ними. Пауза
   меньше на время построения, но появляется состояние между шагами. Не выбрано ради простоты.
4. **Отбрасывать раунд при рестарте** (как в A5). Не нужно: без рабочих файлов продолжение безопасно и дешевле.
5. **Запасные варианты Codex (R10), если S4 не выполнится — не в A6, только новым протоколом:**
   - чтение одной партиции несколькими диапазонами страниц с буфером в памяти, ограниченным одной партицией;
     самый дешёвый опыт — разделить чтение одной дорогой партиции N1 на части;
   - порядок шагов по ожидаемой работе (доказательству покрытия числовой порядок не нужен); самый дешёвый опыт —
     переставить чтение двух сопоставимых партиций относительно пакетов записи.
